# Template notes

For the people who maintain this template (template-only: it is not copied into merchant repos).

## 1. Adapting an existing storefront to this template

The template was extracted from a production merchant storefront. Its locked namespaces and config names were
brand-flavoured and were renamed to neutral ones. To move an existing storefront that still uses the old, brand-specific
names onto the template, apply its design layer over the template's design layer and keep the neutral names below.
(`<Brand>` / `<BRAND>` stand for the old site's own prefix; the original names are intentionally not recorded here.)

| Old (existing storefront) | New (template) | Where |
| --- | --- | --- |
| `window.<Brand>Commerce` | `window.ShopCommerce` | `public/commerce/*.js`, `public/app.js`, `public/commerce/public-api.json` (top-level keys `ShopCommerce`, `ShopCommerce.cart`, `ShopCommerce.checkout`), `scripts/check-layers.mjs`, docs, skills |
| `window.<BRAND>_CONFIG` | `window.SHOP_CONFIG` | `public/config.js`, `public/commerce/api.js`, `public/app.js`, `public/config.local.js`, `check-layers.mjs` (sandbox stub, readable-keys check) |
| `window.<BRAND>_CONTENT` | `window.SHOP_CONTENT` | `public/content.js`, `public/app.js` |
| `localStorage` keys `<brand>:cart`, `<brand>:cart:<hash>` | `shopcommerce:cart`, `shopcommerce:cart:<hash>` | `public/commerce/cart.js` |
| `sessionStorage` keys `<brand>:orderAccessToken`, `<brand>:orderAccessOrderId` | `shopcommerce:orderAccessToken`, `shopcommerce:orderAccessOrderId` | `public/commerce/checkout.js` |
| guard pattern: no `'<brand>:...'` keys in design code | no `'shopcommerce:...'` keys | `scripts/check-layers.mjs` |
| `window.<ADMIN>_CONFIG` (admin) | `window.ADMIN_CONFIG` | `admin/config.js`, `admin/lib/api.js`, `admin/scripts/lib/ctx-surface.mjs`, `admin/e2e/run.mjs`, `admin/config.local.js` |
| admin `sessionStorage` keys `<admin>.refresh`, `<admin>.accessReloadAt` | `admin.refresh`, `admin.accessReloadAt` | `admin/lib/api.js`, `admin/e2e/run.mjs`, guard fixtures |
| admin guard temp dir prefix `<admin>-guard-` | `admin-guard-` | `admin/scripts/test-guard.mjs` |
| a hard-coded seed script with `SEED_*` env | `scripts/import-catalog.mjs` (`IMPORT_*` env, JSON input `catalog/catalog.sample.json`) | `scripts/` |
| `wrangler.jsonc` `"name"` of the old site | merchant slug (set by `new-merchant.mjs`) | `wrangler.jsonc` |
| site-specific product photos and backgrounds | `og-cover.png`, `story.png` (generated by `scripts/gen-placeholders.mjs`); sample product photos in `catalog/images/` | `public/assets/`, `catalog/` |
| project-workflow folders of the old site (change proposals, workflow skills and commands) | not carried over | |

Consequences to plan for when moving such a site onto the new names:

* Returning visitors lose their saved cart (the old `<brand>:cart:*` keys are no longer read) and an in-flight order-status
  token in `sessionStorage` once. That is acceptable for a one-time switch, but do it outside peak hours. The cart code still
  deletes the old unscoped legacy key name `shopcommerce:cart` only; it does not know the old brand keys.
* Admin users on a localhost body-mode session are logged out once (`admin.refresh` is a new key). Production uses the
  HttpOnly cookie mode, which is unaffected.
* The `config.js` of that site keeps its real `apiBase` / `publishableKey` (merchant-owned): create the new repo with
  `scripts/new-merchant.mjs --api-base ... --publishable-key ...` or edit `config.js` and re-lock.

## 2. Every change made to locked code relative to the original site

Behaviour of the locked code is unchanged except for the items marked **(behaviour)**.

1. The renames above (`public/commerce/**`, `public-api.json`, `admin/lib/api.js`, `admin/config.js`, guard scripts,
   `admin/e2e/**`, guard fixtures). Mechanical, no logic change.
2. `scripts/check-layers.mjs` **(behaviour)**: reads `template.json`; the `REPLACE_WITH_*` placeholder rule now applies
   only when `isTemplate` is not `false`; in a merchant repo leftover placeholders are a warning and the hash manifest
   is the only protection. Fails when `template.json` is missing or invalid.
3. `scripts/check-scope.mjs` **(behaviour)**: the allowed paths come from `template.json` (`sites.<site>.designPaths`,
   read from the base ref so a branch cannot widen its own scope) instead of a hard-coded list. The same paths as before.
4. `admin/index.html`: Google Fonts `<link>`s (preconnect and stylesheet) removed; title `商店後台`; neutral favicon and
   `theme-color`. **(behaviour: no third-party font requests.)**
5. `admin/design-defaults/**`: re-synced from the neutral `admin/design/**` (tokens, copy strings with flower wording,
   placeholders in `product-edit.js`). This is the locked fallback copy of the design layer and is identical to it.
6. `admin/styles.css`: warm brand colours in a few hard-coded rules replaced by the neutral palette; header comment.
7. `admin/e2e/{data,run}.mjs`: neutral test data (no flower names); function renamed `restockFlowers` -> `restockStock`.
8. Comments / log text that named the original site (`admin/scripts/serve.mjs`, `check-design.mjs`).
9. Hash manifests regenerated with `--update` for the template: `scripts/commerce.manifest.json` and
   `admin/scripts/core.manifest.json`.
10. New locked files: `scripts/{check-locked,sync-core,import-catalog}.mjs`, `scripts/lib/template.mjs`,
    `admin/deploy/**`, `.github/workflows/guards.yml`, `docs/CORE-CHANGELOG.md`, `*.example` config files.

### v0.2.0 (2026-11-25, decisions in docs/DECISIONS.md)

11. **(behaviour)** `public/_headers` (new, locked, hash-protected, synced): the strict storefront CSP. `scripts/check-layers.mjs`
    verifies it and flags inline scripts in `public/index.html`. `public/commerce/local-config.js` (new, locked) replaces the inline
    localhost-override script of `index.html`. Why `style-src-attr 'unsafe-inline'`: `app.js` builds product photos with inline

    "刪除後無法復原。" (the old dialog only reassured that products stay). `lib/public-api.json` (the `ctx` surface) did not change.

## 3. Known limitations

* **The variant option key is `size` (S / M / L).** The storefront reads `sku.options.size`; `S`, `M`, `L` are listed
  first and in that order, any other value (`Free`, `XL`, `500ml`) is listed after them with its raw text as the label;
  the default price on cards is the `M` SKU, else the first SKU. A SKU without `options.size` cannot be added to the cart
  (no size button is rendered). The admin product editor offers exactly S / M / L (other SKUs of a product are kept
  untouched and reported, never deleted), and its e2e suite assumes S/M/L. Supporting other option schemes is a core
  change (storefront `app.js` display + `cart.add` call, admin `lib/catalog.js` / product form).
* The core is Taiwan-flavoured: TWD integer amounts, `Asia/Taipei` dates, Traditional Chinese copy, the `new-arrivals`
  category slug (the admin offers to create a category called 本季新品 with that slug).
* The hash manifests protect `public/commerce/**` and `public/config.js` (storefront) and the whole admin core, not the
  guard scripts themselves; those are protected by scope (`check-scope`, `check-locked`) and review. A PR can edit the
  workflow file, so branch protection plus required review on `.github/**` is a human step on GitHub.
* `admin/design-defaults/` duplicates `admin/design/` by design (the fallback screens). Any change to a default screen
  must be copied to both (see `CLAUDE.md`, section B).
* HEIC conversion under the strict CSP of `admin/deploy/nginx.conf.template` (the vendored converter uses a blob
  worker) is allowed by `worker-src blob:`; non-Safari HEIC upload under that CSP was not exercised in the template's
  tests (the e2e CSP section uploads a JPEG).
* `admin/deploy/Dockerfile` and the nginx config were written against the platform runbook and not deployed.
* The storefront has no `<noscript>` fallback and no server rendering (static, hash routes); link previews use only the
  static `index.html` metadata.
* `import-catalog.mjs` reads JSON only (no CSV), never deletes, and detects "image already uploaded" by file name only
  (replacing a photo under the same name is not detected).
* Placeholder prices, copy and images are placeholders. Never ship the sample catalogue to a real shop.
* The sample admin e2e needs a platform checkout next to this repo (`../ecommerce`, override `ECOMMERCE_DIR`) and a
  throwaway stack; the full multi-section run takes 40+ minutes.

## 4. Open decisions

Items 1 to 3 were decided on 2026-11-25 (docs/DECISIONS.md D5): merchants are created with `new-merchant.mjs`, `sync-core` is run by a human per merchant, and the sync source is an annotated tag only (`--allow-untagged` is the recorded emergency override).

1. **How merchant repos are created in production**: `scripts/new-merchant.mjs` (one command, sets the brand and the
   config, re-locks manifests) versus GitHub's "Use this template" button (copies files without history, no
   customisation). Recommended: mark this repo as a GitHub template for discoverability but create merchants with the
   script, then push the result to a new repo.
2. **Who runs `sync-core`** (a human per merchant, or the platform opening a PR from a version tag) and where its
   approval happens. The script is built for a human; a platform wrapper should still require a human merge.
3. **Version tags**: tags `vX.Y.Z` on this repo are the distribution unit. Decide whether `main` may be used as a sync
   source (the script only needs a clean checkout whose version is higher).
4. **`config.js` placement**: it is locked and hash-protected but merchant-owned. A cleaner long-term shape may be a
   separate merchant-owned file outside the locked layer; kept as is because the guard and the skills rely on it.
5. **Generalising the `size` assumption** (limitation above): whether to schedule a core change for arbitrary option
   schemes before more categories of merchants are onboarded.
6. **Branch protection / required workflows** on GitHub and a code-owner rule for `.github/**` and the locked paths.
7. **Template CI**: `tests/run.mjs` runs in CI for the template only (the workflow step is skipped in merchant repos).
   Decide whether to also run the throwaway-stack e2e in CI (needs the platform repo and Docker).
8. **Admin logo / branding**: the platform's `admin_branding` hook can override accent and primary colour at runtime;
   the template's default logo is a placeholder in `admin/design/assets/logo.svg`.

9. **Pin `connect-src` / `img-src` of the storefront CSP per merchant** (needs the API and image origins in a merchant-owned
   copy of `public/_headers`, written by `new-merchant.mjs`; sync would then have to leave the file alone, so CSP upgrades would
   need a manual merge). Today the policy allows any `https:` origin for those two directives.
10. **Content store roadmap (not built, do not build content fetching yet).** The platform has per-shop content schema registration
    (built, human only). Still to come on the platform: content documents by key, revisions, the public `GET /shop/content*` read and
    preview endpoints, the publish hook. Then, in the template: a locked `ShopCommerce.content` loader (read with the publishable
    key, cache, fall back to `content.js` defaults), the design layer reading it instead of `content.js`, the admin core's content
    form functions (edit, preview, publish against the registered schema; new `ctx` functions, so a human-reviewed core change per
    `.claude/skills/core-change`), and a `content_schema_registered` check in onboarding. Until then `content.js` is the source and
    `public/content.schema.json` is the contract it will move to (a test keeps them aligned).
11. **GitHub**: create the repo, protect `main`, require the `guards` check and a code owner for `.github/**` and the locked paths;
    push the tags (`git push origin v0.2.0`). Nothing in this repo creates a remote.
12. **Adapting an existing storefront to the template**: apply its design layer over the template's with
    `scripts/new-merchant.mjs`, mind the v0.2.0 design-layer actions (copy key rename, index.html inline script, content schema file,
    `titleHtml`), and follow the guide in section 1.

## 5. Running the browser tests on a throwaway stack

Never against the main `ecommerce` database, the tunnel or Cloudflare; never `docker compose down -v`. Needs the
platform checkout next to this repo (`../ecommerce`, or `ECOMMERCE_DIR`) with its docker-compose infra running.

```bash
bash tests/e2e/stack-up.sh                      # DB merchant_template_dev, migrate + seed -demo, API on 127.0.0.1:8180 (REDIS_DB=1, mock payments)
# import the sample catalogue (super admin from the platform .env, never typed or printed) and register the storefront origin
IMPORT_API_BASE=http://127.0.0.1:8180 IMPORT_ADMIN_EMAIL=... IMPORT_ADMIN_PASSWORD=... IMPORT_ORIGIN=http://localhost:8788 \
  node scripts/import-catalog.mjs catalog/catalog.sample.json
node tests/e2e/prepare.mjs                      # hide the platform demo seed's own products
node tests/e2e/serve-storefront.mjs &           # http://localhost:8788 (virtual config.local.js, nothing written)
E2E_OUT=<dir> node tests/e2e/storefront.mjs     # home, category, product, bag, guest checkout (mock payment), order status; 390 + 1280
cp admin/config.local.js.example admin/config.local.js
(cd admin && node scripts/serve.mjs --proxy http://127.0.0.1:8180 &)
(cd admin && node e2e/setup.mjs && E2E_OUT=<dir> node e2e/smoke.mjs && E2E_OUT=<dir> node e2e/design.mjs)
rm admin/config.local.js; bash tests/e2e/stack-down.sh   # stop, DROP DATABASE, FLUSHDB redis 1, empty the e2e bucket
```

`admin/e2e/run.mjs` is the full multi-section suite (40+ minutes); `smoke.mjs` plus `design.mjs` is the quick subset.
Note that the platform's own demo seed adds a few products of its own (some with flower-like names); they are the
platform's data, not the template's, and `prepare.mjs` hides them.
