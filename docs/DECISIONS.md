# Decisions

Standing decisions about the merchant template and every merchant repo made from it. Each one was **decided by the user**
(the template's owner) and is enforced by the tooling named next to it; changing one is a human decision, recorded here
first. Newest first. This file is part of the locked core (it is synced to merchant repos so design sessions can read it).

## 2026-11-28, decided by the owner

### D26. Storefront network scan: methods named like a keyword and computed-key methods declare their parameters (two D24 residual false positives)

Decided by the owner ("following the recommendation"; a guard rule change under D10: independent review required). It only removes two false positives of the D24 scoped `declaredNames` (`scripts/check-layers.mjs` step 5f); the scan stays fail closed and no refusal is removed. No `ctx` function, `ShopCommerce` function, route or CSP change; no design-layer action. `scripts/lib/html-scan.mjs`, `admin/scripts/check-design.mjs` and the admin scan are unchanged (the admin scan bans the bare names `top`, `self`, `parent`... outright and has no scoped declarations).

* **Method named like a keyword.** `CONTROL_WORDS` (the words that may not start a method definition) listed 22 words. A method or object member named `delete`, `new`, `return`, `typeof`, `void`, `in`, `of`, `yield`, `throw`, `case`, `else`, `do` or `instanceof` (`class K { delete(top) { const { open: o } = top; } }`) was therefore not seen as a method, so its parameter was not a declaration and the legal code was refused. Only words for which `word (...) {` on one line is something other than a method stay excluded: the block heads (`if for while switch catch with await`), `function` (its parameters are read from the `function` itself) and `extends` (`class A` newline `extends (top) {`). Every other word followed by `(...)` and a `{` on the same line is a syntax error anywhere but a method definition, so it can only be a method; the definition context (start of a member, or after `{ } , ;`) and the same-line `{` rules of D24 still apply.
* **Computed-key methods.** `[expr](params) { ... }`, also after `static`, `async`, `get`, `set` and `*` (`class K { [Symbol.iterator](top) {...} }`, `{ ['a' + 'b'](self) {...} }`), was not matched at all (the rule wants an identifier before the parenthesis). New step 3b reads it with the same definition context and same-line `{` as a named method. The parameters are visible only inside the method: the KEY expression is outside their scope, so `{ [({ open: q } = top, 'k')](top) {} }`, `{ [window.open](x) {} }`, `{ [fetch](x) {} }` and `{ ['fe' + 'tch'](x) {} }` are still refused, as are `const a = [f](top)`, `x = a[k](top)` newline `{ ... }`, and `x = [f](top) { ... }` (an array literal or an index followed by a call is not a method).
* **Tests** (`tests/storefront-origins.test.mjs`): 10 allowed and 26 refused cases, including `delete(top) {}` against `function () { delete top.x }`, `delete (top).x`, `delete (top)` newline `{ ... }` and `class A` newline `extends (top) {`; mutation tests restore the old keyword list or remove step 3b (the allowed cases are refused again) and widen each new condition (definition context, same-line brace, `extends`, scope: the refused cases pass), so each rule is shown to be needed. The D24 mutation test anchors were moved to the right step.
* **Still residual (unchanged, fail closed):** a method literally named `if`, `for`, `while`, `switch`, `catch`, `with`, `await`, `function` or `extends` that declares a parameter named like a global object is still refused (rename the method or the parameter); the lexical limits of D24 (arrow function expression bodies end at the first `;`, `,` or line break; a top-level `let` / `const` / `class` of a global-object name is trusted) and D23 (b) to (d).

**Guard rules and scripts changed by D26 (for the independent review):** `scripts/check-layers.mjs` (`CONTROL_WORDS`, new step 3b of `declaredNames`) only. No manifest changes: `scripts/check-layers.mjs` is not hashed in `scripts/commerce.manifest.json`, and `admin/scripts/core.manifest.json` covers only the admin files (`node admin/scripts/check-design.mjs --update` was run and wrote the same hashes).

### D24. Follow-ups of D23: a real HTML tokenizer for the index.html scans, scoped declarations in the storefront network scan, and the three e2e flakes (stat-card order, order-number search, canary 404)

Decided by the owner (items 1 and 2 are guard rule changes: independent review required under D10; the exact list is at the end). No new `ctx` function, `ShopCommerce` function, route or CSP change; the only design-layer action is item 3a.

**1. HTML tokenizer (`scripts/lib/html-scan.mjs`, copied byte for byte to `admin/scripts/lib/html-scan.mjs`; a test fails when the copies differ).** A small tokenizer that follows the WHATWG states: data, RCDATA (`title`, `textarea`), RAWTEXT (`style`, `xmp`, `iframe`, `noembed`, `noframes`, `noscript` with scripting on), script data with its escaped and double escaped states, PLAINTEXT, tags and attributes (duplicate attribute: the first wins; `>` inside a quoted value), comments (`-->`, `--!>`, `<!-->`, `<!--->`, unterminated), bogus comments (`<?`, `<!x`, `</ `, `<![CDATA[` outside foreign content) and DOCTYPE. After a start tag it does the one thing the tree builder does to tokenization: it switches to the text state of that element. So `<!--` inside `<style>`, `<title>`, `<textarea>`, `<noscript>` or `<script src>` is NOT a comment and the D23 documented bypass `<style><!-- </style><script>evil()</script> --></style>` is now found. An end tag cut off by the end of the input (`</script x`) is not part of the script text, as in a browser. Used by `admin/scripts/check-design.mjs` (`inlineScripts`, `indexHtmlProblems`, `importMapHash`) and `scripts/check-layers.mjs` (step 5 inline script / `on*=` check, step 5b script order, which now also sees an unquoted `src`). `on*=` is still looked for in the comment-free text.
   * Fail closed where the scan does not model the parse: a start tag `<svg>`, `<math>` (foreign content), `<select>` or `<frameset>` anywhere in `index.html` is reported (`index.html contains <svg>...`): an error in the admin check and in the template, a warning in a merchant repo (the same severity as an inline script there). The real `admin/index.html` and `public/index.html` have none; a design that needs an inline SVG keeps it in `app.js` or an asset file.
   * Differential test against Chromium (`tests/e2e/html-scan-differential.mjs`, in `ci-browser.mjs`, Playwright 1.65.1): for every case the browser's DOM is compared with the scanner: the list of `<script>` elements (has `src`, exact text), the number of comment nodes, and that every marker `R(n)` that really ran sits in a script the scanner reports as inline. The corpus has the D23 variants, 85 hand-written cases of every state, and seeded random sequences of 2 to 13 fragments (comments, raw text, script, quotes, tags). The development run covered about 90,000 cases (seeds 1, 7, 11, 20,000 per stream and more) with 0 mismatches after two real bugs it found in the first version (a comment node count of `<?x>` is a processing instruction in Chromium; an end tag cut off by the end of the input). Mutation tests (`tests/html-scan.test.mjs`) remove one tokenizer feature at a time and show the D23 variants pass again.
   * Not covered, said plainly: the tree builder beyond the four elements above (for example `<template>` content is tokenized like normal text, which is what a browser does; a `<noscript>` with scripting OFF would be markup, but the admin and storefront run with scripting on); CRLF in an import map text is hashed as written (the guard's manifest already normalizes CRLF; deployment files are LF); Firefox and Safari were not run.

**2. Scoped declarations in the storefront network scan (`scripts/check-layers.mjs` 5f).** `declaredNames` returned a set of names for the WHOLE file as soon as any declaration existed, a parameter included. It now returns `(name, position) => declared where it is used`: a top-level `var / let / const / function / class` covers the file; a `let / const / class / function` in a block covers that block; `var` covers its function body; a `for (const x ...)` head covers the loop; parameters (function, method, arrow, destructured, defaults and rest handled by a binding parser) and a `catch` binding cover only their own function or catch body (an arrow with an expression body: to the end of the expression); a named function expression's name covers its own body. A destructured KEY, a default value, a call argument (`g(self)`), `extends mix(top) {` or a call followed by a block on the next line (`foo(top)` newline `{ ... }`) does not declare: a method definition needs a definition context (start of a class or object member, or after `{ } , ;`) and its `{` on the line of its `)`. Anonymous functions and methods named like keywords (`x.delete(function () {...})`, `{ catch(e) {...} }`) are function bodies; only the heads `if for while switch catch with await` open a plain block (independent review M1, M2).
   * **Top-level `var` / `function` of a global-object name (review L1).** In a classic script a top-level `var top`, `var location`, `var self;` or `function parent() {}` does not replace the browser's own binding (`top` and `location` are unforgeable, `var self;` assigns nothing), so it no longer exempts `top`, `self`, `parent`, `frames`, `window`, `globalThis`, `location`, `history` or `document` anywhere. A top-level `let` / `const` / `class` still does (it shadows, or the script throws and never runs); inside a function or block `var` and everything else are scoped as above. A design file that has `var parent = ...` at the top of a classic script now has to use `const` / `let` or put it inside a function. Closes the D23 residual (a): `function g(top) {}` plus `const { open: o } = top` is refused again, in every case of the list in the tests (and the same `var { location: l } = self` / `var l = location` forms). Also fixed on the way: the string-concatenation join (`'op' + 'en'`) now keeps the text length (padding), so positions stay valid for the scoped check. Tests: the cases in `tests/storefront-origins.test.mjs` (38 refused, 20 allowed), mutation tests that widen each scope again and show the refused cases pass, 0 differences against the old scan on the real storefront design files (`bouquet`, `bouquet-next`, the template). Still residual (D23 b to d, unchanged): indirect access (`this.open`, `document.defaultView.open`, `{ ...window }`, `eval`, a string for `setTimeout`, `with`), incomplete alias forms (`var a = window.location.assign`, `fn(window.location)`) and non-literal keys. The strict CSP remains the real defence.

**3. e2e stabilisation (run on a throwaway stack: database `merchant_template_dev`, API 8180, admin 3001; all of it stopped and dropped afterwards).**
   * **3a. Home stat cards (`admin/design-defaults/views/home.js`, copied to `admin/design/views/home.js`; DESIGN layer).** The five cards come from separate requests; the first was `prepend`ed and the others `append`ed in the order the requests finished, so the row order changed from run to run (parity screenshots). Each card now has a fixed slot (today 0, unshipped 1, low stock 2, products 3, shipping 4) and is inserted before the first card with a later slot, so the order is the same however the requests complete; a failed request still leaves no card. Design-layer action for a merchant that has its own `views/home.js`: take the same `place()` change (or leave it: only the order of the cards is affected). Tested in a real browser with the answers delayed in every permutation (`admin/e2e/home-order.mjs`).
   * **3b. "search by order number" timeout (`admin/e2e/run.mjs`).** Root cause found, not a slow query and not a missing wait: the API matches `q` against recipient name, phone (`ILIKE %q%`) AND the order id, newest first. On a fresh database the ids are small (2, 5, 9) and occur inside the phone numbers of almost every other order, so order 2 was the LAST of 29 matches and not on page 1; the step waited for a card that was on page 2. Measured on the throwaway stack: `q=9`, `q=6`, `q=5`, `q=2` 29 matches each, the order itself not on page 1 (5 of 29 ids), `q=4` 23 matches. The step now waits for the answer to its own query and then looks through the pages. No timeout was changed. (A product change, exact id first, is a platform API decision; not made here.)
   * **3c. Console 404 in "no console errors" (`admin/e2e/lib/expected-noise.mjs`).** The 404 is the canary's expected `/deny/lib/canary/target.js` (D19), not a missing file. The helper allowed one per document and handed the allowance back at the page's `load` event. That is a race: the canary starts after app.js, so with a slow resource the new document's 404 is logged BEFORE its `load` event while the previous document's 404 was logged AFTER its own; the second then counted as an error. Reproduced for real (a delayed `/deny/` answer and a slow image: the console error appears), and fixed by counting main-frame navigation requests (redirect hops excluded) instead of `load` events: one allowance per document load, over the whole page. A surplus canary 404, any other `/deny/` hit and every other 404 are still errors. Not a missing screenshot folder: the folder was only the correlated slow start.

**Review follow-ups (independent review of PR #16: fixes M1 to M3 and the cheap L items).** The event handler (`on*=`) check of step 5 now also uses the tokenizer's attribute NAMES, so unquoted `<img src=x onerror=alert(1)>` and `<img/onerror="x">` are found (L2). Duplicate attributes: the FIRST value wins in the standard and in the tokenizer (`<script src=a src>`, `<script type=importmap type=x>`); the browser differential compares `src` and `type` values and a mutation test catches a tokenizer that keeps the last (L5). Character references in attribute values are NOT decoded: `type="&#105;mportmap"` is therefore not the import map and counts as an extra inline script (refused), and a `src` with a reference never equals a script-order name (error); neither can make the scan accept what a browser treats as something else (L3, tested for `type`). The canary allowance of `canaryNoise` accumulates per page: a document that is cancelled before its canary ran leaves its allowance for a later one, so a duplicate canary 404 on a later document could be tolerated once (L4, accepted: it never hides any other URL or status). **Residuals after the review:** the scoped check is lexical on the masked text, not a parser: an arrow function with an expression body ends at the first `;`, `,` or line break (an unusual layout may exempt less than it should, never more); a global-object name introduced by a top-level `let` / `const` / `class` is trusted as a real shadow; everything in D23 (b) to (d) is unchanged.

**Guard rules and scripts changed by D24 (for the independent review):** (1) `scripts/lib/html-scan.mjs` and `admin/scripts/lib/html-scan.mjs` (new, identical); `admin/scripts/check-design.mjs` (`inlineScripts` now uses the tokenizer; `indexHtmlProblems` adds the refusal of `<svg>`, `<math>`, `<select>`, `<frameset>`); `scripts/check-layers.mjs` (step 5 uses the tokenizer, adds the same refusal as error/warning; step 5b uses the tokenizer's script `src`). (2) `scripts/check-layers.mjs` step 5f: `declaredNames` scoped (see above); `joinStringConcats` keeps the length; the three call sites pass a position. Not guard rules: `admin/design-defaults/views/home.js` (design layer file of the core), `admin/e2e/*` (test only). Manifests re-locked with the documented `--update` commands only; no `ctx`, `lockedPaths` or `template.json` change.

### D23. Cleanup of known residuals: tighter storefront scan (bare `open(`, global destructuring and aliases), inline-script tokenizer gaps, a canary that does not follow redirects, and e2e stabilisation

Decided by the owner (the guard-rule tightening of items 1 and 2 below needs the owner under D10; it gets an independent review). Every item closes a residual that earlier reviews listed; none adds a `ctx` function, a `ShopCommerce` function, a route or a CSP change, and there is no design-layer action.

**1. Storefront scan, `scripts/check-layers.mjs` step 5f (guard rule change).** (a) A bare `open(...)` call is `window.open`. Before, ANY declaration of a binding named `open` anywhere in the file (a variable, a parameter, a destructured name, an arrow) exempted the whole file, so `const open = window['op' + 'en']; open(url)` passed. Now only a genuine FUNCTION declaration (`function open() {}`, also `async` and generator forms) exempts the file, and a method definition (`{ open() {} }`, `class { open() {} }`) is still skipped call by call. A local variable, parameter or arrow named `open` that is CALLED is refused (rename it); a variable named `open` that is never called as `open(` is untouched (`public/app.js` has one). (b) New: `open`, `location` and `history` may not be taken out of a global object by destructuring (`const { open } = window`, `({ open: o } = globalThis)`, `{ location: { href } } = window`, a computed key `{ ['op' + 'en']: o } = window`, a rest pattern `{ ...r } = self`), nor aliased (`const l = window.location`, `= location`, `= history`, `= document.location`), nor read with the exact string (`window['open']`, `self?.['location']`, `window['op' + 'en']` after joining string concatenation, `Reflect.get(window, 'open')`). Reading through the property (`location.hash`, `history.replaceState(...)`, `window.location.href`, `const { hash } = location`) stays allowed because the storefront router uses it. A local `top` / `parent` / `self` declared in the file still means "not the global" as before. Residual that remains (the CSP is the fence): names built from non-literals, and `this.open` at the top level.

**2. Inline-script tokenizer gaps (three of them; not a full tokenizer, see the limit below).** (a) `admin/scripts/check-design.mjs` `inlineScripts()` (the index.html import-map rule) and `scripts/check-layers.mjs` (the storefront `index.html` inline-script and script-order checks) removed HTML comments with a regex that waited for `-->`. A browser also ends a comment at `--!>`, so `<!-- x --!><script>...</script> -->` hid a live script. Both now end a comment at `-->` or `--!>` and treat `<!-->` and `<!--->` as empty comments. (b) An unterminated `<script>` (no closing `>` of the start tag, or no `</script` after it) used to match nothing and so passed in the admin check; it now yields a violation (`deploy/importmap`, "never closed"), never counts as the import map, and an end tag with attributes (`</script x>`) ends a script as in a browser. The storefront check already refused any `<script` without `src`.

**3. Canary "unverifiable" paths (`admin/lib/canary/probe.js`, locked core).** The fail-closed 404 case was tested; now also a 200 that is not JavaScript (text/html), a redirect and a dropped connection (`admin/e2e/import-map.mjs` cases g, h, i, which expect the design layer to stay off with reason `unverifiable`). The redirect test found a REAL gap: `fetch` followed a redirect to a JavaScript file, saw `200` + JavaScript and reported the isolation as verified although the target itself was not served. The probe now fetches with `redirect: "manual"`, so a redirect is unverifiable (design off). A mutation of each probe condition makes the matching case fail.

**4. Profile follow-ups (D21).** Documented, not changed: the design-history hint is dismissed ONLY by its close button (visiting the profile page does not count; once a name is saved the hint is gone because the session knows the name). The name known to the hint is the one loaded with the session; a name set in another tab or on another device is not noticed until the next sign-in or page load, so the hint can show once more. A refresh on focus was considered and NOT done: it needs a second `GET /admin/me` in the sealed profile capability with its own throttling, race and error handling and changes the e2e request counts, which is not trivial.

**5. e2e noise (NOT changed).** The home-page stat-card ordering race of `admin/e2e/parity.mjs` (the cards of `design-defaults/views/home.js` are added in the order their requests finish) and the occasional "orders by number search" timeout of `admin/e2e/run.mjs` on a cold database need the throwaway ecommerce stack (Postgres, Redis, MinIO, the Go API) and neither reproduces on demand. They were not run in this change and no fix was guessed. Note for whoever does: waiting for all five cards fixes the half-rendered screenshot but not the ORDER (that needs the view to fill fixed slots, a design-defaults change), and the search step already waits for the expected card, so a longer timeout would only hide a slow query.

**Not detected / residuals of D23 (stated plainly; the strict CSP, with `connect-src` and `img-src` pinned to the merchant's origins, is the real defence for all of these, 5e).** (a) `declaredNames` exempts a name for the WHOLE file as soon as the file declares it anywhere, parameters included, so a file that contains `function g(top) {}`, `g(self)`, `g(parent)`, `g(location)` or `g(history)` lets a later `const { open: o } = top; o('x')`, `var { location: l } = self` or `var l = location; l.assign(x)` pass. (b) Aliasing is incomplete: `var a = window.location.assign`, `[window.location]`, `fn(window.location)`, a ternary or `||` value, `for (x of [window.location])`, `var { assign } = location`, `location.assign.bind(location)` and `Object.assign(location, { href })` are not recognised. (c) Indirect access is not seen: non-literal keys (`window[k + 'en']`), `this.open` / `this['open']`, `document.defaultView.open`, `[window][0]`, `{ ...window }`, `Reflect['get']`, `eval`, a string given to `setTimeout`, `with (window) { var f = open }`, and passing `window` as an argument. (d) Navigation through `location['href'] = ...` or `location["ass" + "ign"]()` is not scanned. A real fix for all of these is a proper parser, a follow-up.

**Limit of the HTML comment handling (item 2).** The regex still does not know that `<!--` is NOT a comment inside raw-text and RCDATA elements (`<style>`, `<title>`, `<textarea>`, `<noscript>`) or inside a `<script src>`: `<style><!-- </style><script>evil()</script> --></style>` hides a script from `indexHtmlProblems` (and from the storefront check). The admin relies on the hash-based CSP (D19) as the backstop, the storefront on its strict CSP. The tokenizer gaps are therefore NOT all closed: only `--!>`, `<!-->`, `<!--->` and the unterminated script are. The real fix is a proper HTML tokenizer (follow-up).

**Guard rules and scripts changed by D23 (for the independent review):** `scripts/check-layers.mjs` (storefront scan: bare `open(` exemption narrowed, global destructuring / alias / bracket rules added, HTML comment ending) and `admin/scripts/check-design.mjs` (`inlineScripts`, `indexHtmlProblems`). Locked core changed: `admin/lib/canary/probe.js` (not a guard rule; its manifest hash is re-locked with `node admin/scripts/check-design.mjs --update`). Tests: `tests/storefront-origins.test.mjs`, `admin/scripts/test-guard.mjs`, `admin/e2e/import-map.mjs`, `tests/workflow.test.mjs` (the runner `tests/e2e/ci-browser.mjs` must exist in the template: deleting it used to make the `browser-tests` job pass silently) and the newest-first order checks of the decision ids.

### D22. The real-browser suites that need only this repository run in CI and can no longer be skipped silently; the suites that need the ecommerce stack stay local

Decided by the owner (CI only: no guard rule, `ctx`, `lockedPaths` entry or manifest procedure changed; no design-layer action). Before this, the Playwright suites printed `SKIP ... Playwright not found` and exited 0 when Playwright or Chromium was missing, and GitHub Actions had neither, so the whole browser coverage was skipped there without anyone noticing.

**How a suite skips, and the flag.** Each standalone suite looked for Playwright in `$PLAYWRIGHT_DIR` (a folder with `node_modules/playwright`) and skipped when it, or Chromium, was missing. They now call `skipOrFail()` of `admin/e2e/lib/require-browser.mjs`: with `REQUIRE_BROWSER_TESTS=1` the same condition is a FAILURE (exit 1); without the flag nothing changes for a developer (still a clean SKIP). The template has no npm dependencies and still has none: CI installs Playwright in a separate folder outside the repository.

**The CI job `browser-tests`** (`.github/workflows/guards.yml`; permissions `contents: read`; no secrets; no `pull_request_target`; third-party actions pinned by full commit SHA) installs the exact pinned `playwright@1.65.1` (`npm install --save-exact`) in `$RUNNER_TEMP`, caches the Chromium download (`~/.cache/ms-playwright`, keyed by the Playwright version) and runs `node tests/e2e/ci-browser.mjs` with `REQUIRE_BROWSER_TESTS=1`. That runner executes each suite as its own process and fails when a suite exits non-zero, prints a SKIP line, or executes zero checks, and asserts that the total number of executed (non-skipped) checks is above zero; the job summary lists the count per suite. Screenshots are uploaded as an artifact only when the job fails: the suites write to the DEFAULT `*_SHOTS` folders under `admin/e2e/out/` and CI sets `E2E_OUT` for content-storefront into the same tree; no traces are produced.

**Runs in CI (stub or fake API plus static servers, nothing private):** `admin/e2e/preview-banner.mjs`, `admin/e2e/d12-runtime.mjs`, `admin/e2e/import-map.mjs`, `admin/e2e/hardening.mjs`, `admin/e2e/profile.mjs`, `admin/e2e/design-history.mjs`, `admin/e2e/design-review.mjs` and `tests/e2e/content-storefront.mjs` (a fake platform API; it now also honours `$PLAYWRIGHT_DIR`). The `tests/*.test.mjs` wrappers of the same scripts keep running in the `template-tests` job, where they may still skip: the `browser-tests` job is the one that cannot.

**Still local only (need the throwaway ecommerce stack built from the private platform repo: Postgres, Redis, MinIO, the Go API, `$PLATFORM_DIR/.env` for the super admin):** `admin/e2e/run.mjs` (the full admin suite) together with the files it imports or runs (`setup.mjs`, `data.mjs`, `content.mjs`, `design.mjs`, `smoke.mjs`, `parity.mjs`; they use `lib.mjs`, which loads Playwright from the platform checkout), and `tests/e2e/storefront.mjs` and `tests/e2e/content-stack.mjs` (with `stack-up.sh`, `prepare.mjs`, `serve-storefront.mjs`). Their procedure is unchanged (admin README, "Testing"). No secret and no checkout of the private repository is added to the workflow.

**Locally,** `REQUIRE_BROWSER_TESTS=1 PLAYWRIGHT_DIR=<folder> node tests/e2e/ci-browser.mjs` reproduces the CI run.

### D21. Personal profile: each admin user sets their own display name, shown to teammates in the design history (core-owned page, no new `ctx` function)

Approved by the owner on 2026-11-27 ("all as recommended"), as a follow-up of the design history (D13 to D15) and its platform change (`docs/design-history.md` in the platform repo: `GET /api/v1/admin/me` returns `display_name`, `PATCH /api/v1/admin/me {display_name}` sets or clears it). Without a name the history shows the platform's neutral fallbacks ("Team member" for a member of the shop, "Platform admin" for anyone else), never an email address or a phone number. **No new `ctx` function and no design-layer API**: `lib/public-api.json`, the `ctx` manifest and `ROUTE_IDS` are unchanged, and no guard rule or CSP rule changed.

**The page.** A new core route `profile` (`/profile`, `core/routes.js`, flag `core: true`, no permission node) is reachable by EVERY signed-in role (owner, editor, staff, also without `design.view`). `app.js` draws it with `core/profile.js` (controller) and `ui/profile.js` (DOM) and never calls `mountView`: `profile` is not in `ROUTE_IDS`, so `design/routes.js` cannot map a view to it (an entry is ignored with the usual warning, and the test asserts it). One field, "顯示名稱", a label bound to the input, the helper text "隊友會在設計歷史中看到這個名稱；請不要填 email 或電話。" (`aria-describedby`), a counter "n / 80" that turns into a text warning past 80, "儲存" and "清除名稱", a status line and a toast on success, `role=alert` error text with `aria-invalid`, focus on the field after an error, Enter submits, 44 px tap targets, a loading state and a failed-load state with a retry button. ### D20. Hardening PR 4 (stage A of D16): merchant-specific storefront origins, a derived `public/_headers`, the storefront network scan and the trust-boundary analysis

Approved by the owner as item "storefront connect-src / img-src tightened to merchant-specific origins via the new sync mechanism" of the stage A hardening plan (D16), **including the sync / manifest-procedure change** that mechanism needs and **the storefront scan reinforcement** that the independent reviews recommended (both guard-script changes, approved by the owner under D10). No new `ctx` or `ShopCommerce` function; the public API files are unchanged.

**The problem.** The storefront runs in the customer's browser (cart, checkout form with name, phone and address, order access token). `public/_headers` carried `connect-src 'self' https:` and `img-src 'self' data: https:`, so any `https` origin was reachable from script (`fetch`, `sendBeacon`, `WebSocket`) or from an image request: a hostile or buggy design layer could send customer data anywhere, and the static scan was the only defence. The file was locked and overwritten by every `sync-core` with the template's copy, so per-merchant origins could not be stored in it (v0.2.1 left this as a known limitation).

**The mechanism.**
1. **Core template** `scripts/headers.core.txt` (locked, synced, identical in every repo): the former `_headers` with one token per configurable directive (style, img, font, connect, frame). **Merchant config** `merchant.headers.json` at the repo root (merchant-owned, HUMAN only, never in `public/`, so never published): `apiOrigin` and `imageOrigin` (required), optional `extraConnect`, `extraImg`, `extraFont`, `extraStyle`, `extraFrame`. **Renderer** `scripts/render-headers.mjs` (locked, no dependencies, deterministic) writes `public/_headers`, which stays committed because Cloudflare reads it from the assets directory, but is **DERIVED**.
2. **Strict validation.** Every value is a bare `https` origin written exactly as the URL parser prints it (lower case, no path, query, userinfo, trailing slash or default port) with a domain name and a letter-only top-level domain: no `https:` / `*` / `data:` / `ws:` scheme source, no wildcard (not even a single-level subdomain: no case for one was shown, and a wildcard on a shared suffix would admit other tenants), no `http:` (a dev server may pass `dev: true` in code, as `tests/e2e/serve-storefront.mjs` does for its local throwaway stack; the file never may), no IP address or `localhost`, unknown keys refused, at most 5 extras for connect and img and 3 for font, style and frame, no duplicates. `script-src` stays `'self'` and `form-action` stays `'self'` plus the two ECPay hosts: neither is configurable.
3. **Rendered policy.** `connect-src 'self' <apiOrigin> <extraConnect>`, `img-src 'self' data: <imageOrigin> <extraImg>`, `font-src 'self' <extraFont>`, `style-src 'self' <extraStyle>`, `frame-src 'none'` (or the declared frames), `script-src 'self'` (no inline), `frame-ancestors 'none'`, `form-action` as before, and every header added in v0.2.1. Fonts: the storefront needs none from outside (self-hosted or system fonts), so `font-src` and `style-src` stay `'self'` unless a merchant declares `extraFont` / `extraStyle`.
4. **Guard (`scripts/check-layers.mjs`, step 5e).** `public/_headers` must be **byte-identical** to the rendering of the current core template and the merchant config (a hand edit or a stale file fails); the config is validated strictly; `checkCsp` additionally refuses a bare scheme, wildcard or `unsafe-*` source in `connect-src`, `img-src`, `font-src`, `style-src` and `frame-src`; the origin of `public/config.js` `apiBase` must be allowed by `apiOrigin` / `extraConnect`. A leftover `replace-with-*` placeholder in `merchant.headers.json` is a **warning in the template and an ERROR in a merchant repo**. `public/_headers` is no longer hashed in `scripts/commerce.manifest.json` (a manifest that still lists it is tolerated and ignored; `--update` drops it).
5. **`sync-core`.** `public/_headers` and `merchant.headers.json` are merchant-owned paths: a sync never copies the template's version of either. After the locked files (including the new core template and renderer) are copied, the sync **re-renders** `public/_headers` from the new core template and this repo's own config, so the merchant's values are preserved across syncs and never replaced by the template placeholders; if the config is invalid the whole sync is rolled back. A merchant without `merchant.headers.json` is refused before anything changes, with the migration text. **Migration (once, a human)** for a merchant created before v0.5.0: copy `merchant.headers.json` from the template, set `apiOrigin` and `imageOrigin`, run `node <template checkout>/scripts/render-headers.mjs --root . --core <template checkout>/scripts/headers.core.txt`, commit, then sync as usual (the running pre-0.5.0 `sync-core` does not know the config, which is why the file must exist first). **`new-merchant`** fills the config from `--api-base` (config.js `apiBase`) and the new `--image-origin`, renders, and re-locks; a missing `--image-origin` leaves the placeholder, which the guard reports as an ERROR until a human fills it in (its own scripted verification passes `--allow-placeholders`; CI and humans do not).
6. **Human-only.** `scripts/check-scope.mjs` already allowed only the design paths, so the config and the rendered file were out of scope for storefront and admin AI sessions; it now also has an explicit deny list (`merchant.headers.json`, `public/_headers`, `scripts/headers.core.txt`, `scripts/render-headers.mjs`) that applies even if a (hostile) `template.json` listed them as design paths. `check-locked` protects `public/_headers` and `merchant.headers.json` through `merchantOwnedPaths` and the core template and renderer through `lockedPaths`. The config is edited by a human, who then runs `node scripts/render-headers.mjs`; it needs no manifest `--update`.

**Storefront network scan (`check-layers.mjs`, step 5f).** On the canonical source (D17: comments blanked, escapes decoded) plus a **masked** view in which the text of string and template literals is blanked: `fetch`, `sendBeacon`, `WebSocket`, `EventSource` and `XMLHttpRequest` are refused as identifiers in any position (`(0, fetch)(x)`, `var f = fetch`, `navigator.sendBeacon`, `window.fetch`, destructuring), except as an object key whose value is a literal (`{ fetch: 1 }`, data); as exact string values after joining `'fe' + 'tch'` and decoding escapes (`window['fetch']`, `globalThis["\x66etch"]`, `Reflect.get(window, 'fetch')`); `new Image`, `new Audio`, `new Worker` and `new SharedWorker` (a script-created element is a request to every allowed origin); `RTCPeerConnection` (WebRTC is outside `connect-src`); `window.open`; dynamic `import()` and `import.meta`. Copy text, comments and look-alikes (`refetch`, `prefetched`, `ImageList`) pass. Core files (`public/commerce/**`, `config.js`) are not design files and stay exempt exactly as before; the template's own design files and the code blocks of the storefront-design skill produce zero findings. This is an early warning and a bypass-resistant net for the cheap cases; the pinned CSP is the actual fence.

**Trust-boundary analysis (storefront, read from the code).**
* *Loading.* Classic scripts, one realm, no bundler: `config.js`, `commerce/local-config.js`, then the core (`api.js`, `cart.js`, `content-allowlist.js`, `content.js`, `checkout.js`, which freezes `ShopCommerce`), then the design layer (`content.js`, `app.js`). Core runs first, so it can capture what it needs; `check-layers` enforces the order.
* *What lives where.* The cart (`localStorage`, key `shopcommerce:cart:<shop hash>`, hashed from the publishable key) and the order access token (`sessionStorage`, `shopcommerce:orderAccessToken` and `...:orderId`) are written and read only by the core; the platform content cache and the content preview token (taken out of the URL at once, kept in a closure) likewise. The customer's checkout form values (name, phone, address, email) live in `state` in `app.js`, i.e. in the design layer: the design layer renders the form, so **it necessarily holds the customer's personal data**. There is no customer account session on the storefront.
* *Leaks that were reachable from the design layer at runtime* and are **fixed here** (cheap, design-layer-only, no public API change): (1) `ShopCommerce._internal` (`apiFetch`, which adds the publishable key and bearer tokens and accepts any path and header, the config and the image-origin registry) was an enumerable property of the global; `checkout.js`, the last core script, now removes it after the earlier scripts took what they need into closures, so design code (or a scan bypass) can no longer call `apiFetch`; (2) `window.SHOP_CONFIG` was a mutable object the core read on every request (`apiBase`, `publishableKey`), so design code could repoint the API client; it is now frozen after the core loads (`local-config.js` runs earlier and is unaffected). Both are tested in the sandbox (`tests/storefront-origins.test.mjs`) and by the storefront e2e.
* *Not fixed, by design or too large for this PR (recommended follow-ups).* (a) `getOrderToken()` and `placeOrder()` hand the **order access token** to the design layer, which passes it to `startPayment(token)`; a core-held token (no token in the API, `startPayment()` and `loadOrderStatus()` read it internally) would remove the last secret from the design layer. It changes `public-api.json`, so it is a design-layer action: its own PR. (b) The checkout form and its values stay in `app.js`; moving the fields into a core-rendered component would be a redesign. (c) Freezing the JavaScript intrinsics (as D18 does for the admin) is not done for the storefront: `Object.prototype` and `Array.prototype` freezing breaks ordinary assignment patterns in third-party-style design code (the override mistake) and, because the design layer already holds the data it could leak, it does not change what egress is possible; the CSP and the scan do. Hooks on `Storage.prototype`, `JSON` or `Promise` can only observe data that design code can read anyway.
* *The decisive control is egress.* With `connect-src` pinned to the merchant's API origin and `img-src` to its image origin, the remaining channels are: requests to the API origin itself (placing orders on the platform is what the storefront does), the image origin (read-only host), **top-level navigation** (`location.href`, `<a href>`, `<meta refresh>`, `window.open`: no CSP directive governs it, `navigate-to` was never shipped; the scan refuses `window.open` but navigation is also what the design layer legitimately uses, so it is not scanned), WebRTC (scanned), DNS prefetch and similar browser hints, and the `form-action` ECPay hosts (a form can only POST to them). These are the residual risks.

**Residual risks, stated plainly.** (1) A design layer that is hostile or buggy and that defeats the scan can still read the customer's data (it renders it) and can leave the page by navigation or hand data to the platform API; the CSP makes the quiet channels (fetch, beacon, socket, image ping, form post) end at the merchant's own two origins. (2) The merchant config is a human responsibility: a careless `extraConnect` widens egress; the guard limits the count and shape, not the trust in the host. (3) `merchant.headers.json` must match what the platform really serves: an image host that differs from `imageOrigin` blocks the product photos (the browser test shows it as a CSP violation); product image URLs come from the API, so a platform move of its image host needs a config change. (4) Cloudflare reads `public/_headers` at deploy; a deployment that does not serve it (another host, a preview service) must carry the same policy over (D1). (5) The scan is a heuristic net on the canonical text; aliasing through computed template-literal names or closures built from data it cannot see is not caught, which is why the CSP is the fence. (6) A merchant that migrates late keeps the pre-0.5.0 `https:` policy until it syncs.

**Review follow-up (same PR, after the independent review).** (a) Line limit: the renderer refuses any rendered line over 2000 characters (Cloudflare limits the length of a `_headers` line) with a clear message; every origin is at most 100 characters, so a full `extraConnect` + `extraImg` configuration (5 + 5) still fits, while the maximum of all five lists does not. (b) `merchant.headers.json` may carry a UTF-8 BOM (ignored); hosts ending in `.local`, `.localhost`, `.internal`, `.lan` or `.home.arpa` and single-label hosts are refused; internationalised `xn--` hosts are accepted as written. (c) `extraRules` (at most 5, `{ path, cacheControl }`, Cache-Control only, validated) is the legitimate place for non-security rules such as long-cache headers on `/assets/*`; any other header is not supported. (d) `sync-core` compares `public/_headers` with the rendering of this repo's current core template + config before it re-renders, and when they differ prints a loud warning with the differing lines (in `--dry-run`: "would re-render ... the manual edits would be LOST"); it still proceeds, because the file is derived. The guard's message for a missing config now carries the migration command, so a rolled-back sync from a pre-0.5.0 merchant shows it. (e) Scan precision (5f): a network name used as a property is refused only on a global receiver (`window`, `globalThis`, `self`, `top`, `parent`, `frames`, `navigator`: `window.fetch`, `(window).fetch`, `self?.fetch`, `navigator.sendBeacon`), not on other objects (`o.fetch`, `api?.fetch`); object keys (`{ fetch: 1 }`, `{ "fetch": 1 }`), `case "fetch":`, destructuring from a non-global object and the contents of regex literals (blanked only where a regex cannot be a division) are data; `const { fetch: f } = window` and the shorthand `{ fetch }` literal are still refused. `fetch(` as a call keeps being refused wherever it appears (the pre-existing D12-era rule). (f) New lexical rules, all on the canonical source: a bare `open(` call, `window?.open`, `(window).open`, `new window.Image`, aliasing a global object (`const w = window`), navigation by `location = ...`, `location.href = ...`, `location.assign(...)` / `replace(...)` unless every string literal of the target starts with `#` (the in-page routes the storefront uses), `createElement` of script, link, iframe, meta, object, embed or base, the `ping` attribute, `navigator.serviceWorker`. Skipped as residual: a global passed as an argument (`(function (w) {...})(window)`), a global reached through a function result or a property chain (`document.defaultView.fetch`), computed names built from non-literals, text-built `<meta http-equiv=refresh>` and `<a href>` navigation, the bracket string `'open'`.

**Second review follow-up (scan false positives).** Aliasing a global object (`const w = window`) and a bare `open(...)` are scope-aware: a name that the file itself declares (variable, destructured name, function, class, parameter, arrow parameter, catch binding; any declaration anywhere in the file exempts the name in that file) is a local, not the browser global, so `function f(parent) { const p = parent }`, a local `top` or `self`, `{ open() {...} }` method shorthand and calls to a locally defined `open` pass, while `const w = window`, `const t = top` with no local `top` and an undeclared `open("x")` are still refused. The `.ping =` rule ignores receivers named `dataset`, `style`, `props`, `state`, `data`, `options`, `opts`, `config` and `settings`. `sync-core --dry-run` (and the real sync) now refuse an invalid `merchant.headers.json` up front with the validation messages and exit 2, changing nothing. Further residual risks of the scan, all covered by the pinned CSP rather than by the scan (and `eval` is blocked by `script-src`): `new (Image)()`, `const I = Image; new I()`, a bare `window.Image` reference, `window.top.location = ...` (navigation through a property chain), `el.innerHTML = "<img src=...>"` (an image request to an origin that `img-src` does not allow is blocked, to the merchant's own image origin is allowed), and `(0, eval)("window")`.

Covered by `tests/storefront-origins.test.mjs` (renderer, validation, derived-file and placeholder guard, scope and locked-path refusals, sync preservation, rollback and migration, new-merchant, the scan fixtures with positives and negatives, the runtime handle and freeze check, this record), the updated `tests/decisions.test.mjs`, `tests/guard-d12.test.mjs`, `tests/scan-lexer.test.mjs`, `tests/content-guards.test.mjs`, `tests/sync-core.test.mjs`, `tests/new-merchant.test.mjs`, and the storefront browser tests, which now serve the policy rendered from `scripts/headers.core.txt` (`tests/e2e/serve-storefront.mjs`) and assert that a request to another https origin is blocked.

### D19. Hardening PR 3 (stage A of D16): import-map isolation of design modules, fail-closed canary, boot-phase seals, and the approved guard CSP rule change

Approved by the owner on 2026-11-28 ("好") as item 3 of the stage A hardening plan, **including an explicit change of a GUARD RULE** (under D10 a guard change needs the owner): the CSP checks of `admin/scripts/check-design.mjs` (`cspProblems` for the server level and every location, and `deployChecks`) used to force `script-src` to be exactly `'self'`. They now allow ONE extra token, the `'sha256-...'` of the exact text of the inline import map in `admin/index.html`, and nothing else. **No new ctx function, no other guard rule, no new scan rule.** There is no equivalent check in `admin/scripts/check-layers.mjs` (it only forbids inline scripts in `config-loader.js`, `config.js` and `index.html` by the pattern `<script>`, which an `importmap` script does not match); the storefront's `scripts/check-layers.mjs` and `public/_headers` are untouched.

**The problem.** Design modules are same-realm, same-origin ES modules loaded by `lib/design.js` with `import()`. The static scan lets them import only relative paths inside `design/`. If the scan is ever bypassed, a hostile module could import the core modules whose closures hold the sealed API client (`lib/orders.js`, `lib/catalog.js`, `lib/content.js` with `putSchema`, `lib/design-review.js` with `approveRequest`, `core/*`, `ui/kit.js`, ...) and use them without the ctx permission checks and confirmations.

**The design.**
1. **Import map** (`admin/index.html`): one inline `<script type="importmap">` on ONE line, before every module script. Scope `/design/`: `"/"`, `"https://"` and `"http://"` go to `/deny/`, `"/design/"` goes to itself. So every module whose URL is under `/design/` can import files under `/design/` only (the design's legitimate set: its own `views/`, `parts/`, `copy.js`, `routes.js`; the scan never allowed more, and `design-defaults/` is imported only by the core). Everything else is sent to `/deny/<path>`, a core-owned URL that answers 404 (`location ^~ /deny/ { return 404; }` in `deploy/nginx.conf.template`; the dev server has no such file), so the import rejects with a TypeError (not `null`, which only warns). The core's own imports (referrer outside the scope) are unaffected. Spellings tested: relative, absolute path, absolute URL, protocol-relative, query string, percent-encoding, `/design/../lib`, dot segments, backslashes, `new URL(..., import.meta.url)`, `data:`, bare, `blob:`, dynamic `import()` with computed specifiers.
2. **Hash mechanism.** Without a CSP hash the browser blocks the inline map and IGNORES it (fail-open), so `script-src` carries `'sha256-<hash of the exact map text>'`. The template has no build step: the hash is a static value in `deploy/nginx.conf.template` (the server CSP and the `/site-config.js` location), verified by the guard on every run (`deploy` step: it recomputes the hash from `index.html` and requires `script-src` to be exactly `'self' 'sha256-<that hash>'`, order tolerant, in the server CSP and in every location that repeats it; any other token (`'unsafe-inline'`, `'unsafe-eval'`, another or a second hash, a nonce, a host, a scheme, `'strict-dynamic'`, `'unsafe-hashes'`, a hash or nonce in any other directive) is `deploy/csp-weak`; `index.html` must have exactly ONE inline script and it must be the import map: rule `deploy/importmap`); the HTML is read by a small tokenizer (comments including `<!-->`, quoted attributes, `data-src` is not `src`), no new rule id. The documented `node scripts/check-design.mjs --update` (human, locked-file flow) now also rewrites the hash in the nginx template after the map changed. The map is one line so CRLF checkouts hash the same.
3. **Fail-closed canary.** `lib/canary/probe.js` (core-locked in `lib/`: a design file cannot be core-owned, so the probe sits outside `design/`) lives in its own DIRECTORY scope, `/lib/canary/`, built like the design scope (same keys: `"/"`, `"https://"` and `"http://"` denied, one allowed prefix, `/lib/canary/allowed/`, mapped to itself), so it exercises a prefix scope of the same kind as the real wall. `app.js` runs it after the seal and the freeze and BEFORE any design module is imported. It checks `HTMLScriptElement.supports("importmap")`, imports a positive control (`lib/canary/allowed/ok.js`, must load), then FETCHES `lib/canary/target.js` (fetch is not subject to import maps; it must answer 200 with a JavaScript content type, else the check reports `unverifiable` and fails closed: a refused import of an unreachable file proves nothing) and finally imports it (must be denied). Only "fetch succeeded AND the import was denied" counts as isolated. If the target RESOLVES (map not in effect: hash missing, unsupported or old browser, map text changed or removed), is unreachable, or the control fails, the design layer is NOT loaded: `loadDesign({ enabled: false })` imports nothing from `design/` and stays off for good, the built-in screens and copy are used, the console warns `[design] custom design is DISABLED ...` with the reason, and the owner sees one calm core-drawn note (`iso.disabled`). The design CSS (`tokens.css`, `theme.css`) stays, being plain `<link>` files that cannot run code.
4. **Boot-phase seals** (defence in depth, same pattern as `takeApi()`; new `lib/boot.js`, closed by `sealApi()`): `lib/perm.js` (`takePermissions`: setPermissions, clearPermissions), `lib/session.js` (`takeSession`: the mutable state, loadSession, login, logout, clearSession, passwordSetup, invitations; the exported `session` is a frozen read-only view and its `user` object is frozen), `core/auth.js` (`takeMakeAuth`), `core/design-actions.js` (`takeDesignActions`), `core/content-actions.js` (`takeContentActions`), `ui/kit.js` (`takeCoreUi`: showCoreDialog, confirmDialog, allowImageOrigin, allowPreviewLinkOrigin). The old named exports are gone. Core behaviour is identical; the offline test scripts call the `take...()` functions (the boot phase is open there). `loadDesign` cannot be called again to switch a disabled design layer on.
5. **nginx**: `location ^~ /deny/ { return 404; }` and, at server level before every location, `if ($request_uri ~* "^[^?]*(%2f|%5c|%2e|//)") { return 404; }`: any request whose PATH (not the query) holds an encoded slash, backslash or dot, or a double slash, is refused for the whole admin. nginx DECODES and MERGES those while the browser's import map only sees the URL as written: `/design/..%2flib/orders.js` would be a fresh copy of a core module, and `/design%2fcopy.js` and `//design/copy.js` serve `design/copy.js` for a URL outside the `/design/` scope (found by the independent review, checked against real nginx 1.27; the browser test shows the first with an emulated decoder). No published file name has such characters (letters, digits and `. _ -` only). The template was also run by hand in nginx:1.27-alpine (`nginx -t` passes; the paths above, `/deny/...` and `/design/..%5clib/...` answer 404; `/design/copy.js`, `/lib/canary/allowed/ok.js`, `/site-config.js` and a query string holding `//` or `%2f` answer 200; the CSP header carries the hash); that check is not part of the automated suites.

**Limits, stated plainly.** (a) **This is not isolation.** A same-origin module can still read the DOM, call anything `ctx` hands out, and call the platform's cookie refresh endpoint itself; `fetch` is banned only statically. A module that obtains a Worker (banned statically; `worker-src` has `blob:`) runs outside the import map. Real isolation (sandboxed iframe or worker, or a DSL) stays POSTPONED (D16, options B, C, D). (b) The wall depends on the server: a server that redirects a URL under `/design/` to a core file gives that file's final URL outside the scope (a redirect to `lib/orders.js` is refused only because a fresh copy of a boot-phase module throws at evaluation; a redirect to a module without a `take...()`, e.g. `lib/dates.js`, resolves). nginx has no such redirect and the guard refuses symlinks in `design/`. (c) Scopes use absolute paths, so the admin must be served at the origin root (it is). (d) The canary tests the probe's scope, not the design scope: a deployment whose map text is valid and hash-matched but has lost the `/design/` scope would pass the canary; the browser test and `tests/import-map-isolation.test.mjs` assert the shipped map's structure. (e) **Firefox and Safari are NOT verified** (only Chromium was run). Import maps with scopes and CSP hashes are standard, but nothing here claims they behave identically; the canary is the fail-closed mechanism: a browser that does not enforce the map turns the custom design OFF instead of leaving it unprotected. Verify them before relying on custom designs there. (f) Not sealed by name (the map is their wall): `lib/orders.js`, `lib/catalog.js`, `lib/content.js`, `lib/design-review.js`, `lib/design-history.js`, `lib/members.js`, `lib/team.js`, `lib/upload.js` and the other data modules, which hold the boot-phase client in their closures. (g) The start-up probe makes the browser log one 404 for `/deny/lib/canary/target.js` in the console on every load; the browser suites ignore exactly that URL.

**Preview hosts and the future AI-edit service.** Every host that serves the admin files (production, preview hosts, the service's preview environments) MUST serve the same CSP with the hash AND the `/deny/` 404 AND the `%` refusal, i.e. the same image. A host that lacks the hash is not broken for the owner: the canary turns the design layer off there, so a preview that "does not show my design" means the CSP or the map is wrong. After a change to the map in `index.html` a human runs `--update`; the service must not touch `index.html`, `deploy/` or `lib/`.

Covered by `admin/e2e/import-map.mjs` (real Chromium, the real CSP read from the nginx template, fake API recording Authorization headers; control runs with the map removed and the canary bypassed, and with an nginx-style decoder and no percent rule, prove the tests can fail), the guard negative tests in `admin/scripts/test-guard.mjs`, `tests/import-map-isolation.test.mjs`, and the updated suites (`hardening`, `design-history`, `design-review`, `design`, `d12-runtime`, which now serve the CSP with the hash).

### D18. Hardening PR 2 (stage A of D16): sealed API, frozen intrinsics, preview host, delayed approve, scan report

1. **Sealed API capability.** `lib/api.js` keeps the authenticated client, the access token and the refresh logic in its closure. There is no `tokens` export and no `.access` getter. The only ways in are `takeApi()`, which works **only during the boot phase** (every core module calls it once at evaluation: the `lib/*` data modules, `lib/session.js`, `core/auth.js`, `app.js`), and `sealApi()`, which `app.js` calls first thing in `boot()`, after every core module was evaluated (the core has no lazy imports) and before the design layer is imported (`lib/design.js` is the only importer). (b) The singleton INSTANCES (`document`, `performance`, `navigator`, `screen`, `history`, `crypto`, `location`, ...) are frozen too and the replaceable accessors on `window` lose their setter, so `performance.now = f` or `Object.defineProperty(document, "createElement", ...)` cannot shadow a method on the instance. ### D17. Hardening PR 1 (stage A of D16): the design scans compare canonical values, not spellings

Approved by the owner on 2026-11-27 as the first item of the stage A hardening plan (D16 (c)); the owner explicitly approved the fix to the guard scripts for this item (under D10 a guard change otherwise needs the owner). This is a DEFENSIVE bug fix of our own static scanner, found by a static review that suspected the hand-written lexer did not normalise Unicode escapes: it did not, and the review of every rule that reads token text found the rest of the gaps below. **No new ctx function, no new rule id, no CSP change, no runtime change, no allow-list widened**; the template's own design code (`admin/design`, `admin/design-defaults`, the storefront paths) still produces zero violations. Reviewed independently like the other core changes (D10).

**The contract (also the first comment of the lexer in `admin/scripts/lib/design-scan.mjs` and the section "How the scan reads your code" of `admin/docs/DESIGN-LAYER.md`).** Every rule compares CANONICAL values: an identifier or property name by its escape-decoded value (`\uXXXX` and `\u{...}` anywhere in the name; non-ASCII ID_Start / ID_Continue characters, ZWNJ and ZWJ belong to a name; no Unicode normalisation, as JavaScript compares code points; `#private` names too); a string literal and a template literal chunk by their COOKED value (`\xHH`, `\uXXXX`, `\u{...}`, legacy octal, `\0`, the single-character escapes, line continuations, identity escapes); line terminators are `\n`, `\r`, `\r\n`, U+2028 and U+2029 everywhere (they end a `//` comment and an unterminated string, and count lines); whitespace is whatever `\s` covers (NBSP, BOM, the Zs spaces). `lex()` keeps `raw` next to the canonical `v` for messages.

**What was found and fixed.** (1) Identifier escapes were not decoded at all: `\u0066etch(...)`, `window.local\u0053torage` and every other banned name, ctx alias and `ctx` shadow spelled with an escape passed the scan. (2) Template literals kept their raw text, so cooked values (`confirm-\x79es`, `<scr\x69pt>`, `<dialog>`) escaped every template rule; string cooking mishandled `\u{...}` without a closing brace (an endless loop in the scan), `\x`/`\u` with bad digits, a `\0` (turned into a question mark), legacy octal escapes and line continuations. (3) A number token swallowed a following property: `1..constructor.constructor("code")()` hid `constructor`. (4) A `//` comment ended only at `\n`, so code after U+2028, U+2029 or a lone CR was hidden. (5) A `/` after `)`, `}` or `]` was always read as a division, so a regex literal in statement position (`if (x) /'/.test(y); fetch(1)`) started a "string" that swallowed the rest of the line; the lexer now tracks parenthesis kinds (`if`, `while`, `for`, `with`, `switch`, `catch`) and whether a `}` ends a block, an object, a function or a class expression, and where that cannot be known (a `}` that may end a block or an object literal, followed by `/`) it lexes both readings (more in (12)) and every rule runs on all of them; an unterminated regex is read as an operator, never as the rest of the line. (6) `a?.[x + y]`, `5[x + y]`, `/re/[x + y]`, a closed template or an object literal followed by `[` were not treated as computed member access, so `js/computed-access` did not apply. (7) Compound assignments (`ctx &&= other`, `||=`, `??=`, `**=`, `>>>=`) were lexed as two tokens, so assigning to `ctx` through them was not `js/ctx-shadow`. (8) A call was only recognised when `(` followed the name directly: `(setTimeout)("code")`, `(0, x.show)()` and `x.show?.()` evaded `js/timer-string` and `js/dialog-api`; `Object?.values(ctx)` and `Object["values"](ctx)` evaded `js/ctx-unknown`. (9) String keys: `el["popoverTargetElement"]`, `el["onclick"] = fn` and `ev["view"]` were not flagged although `.popoverTargetElement`, `.onclick =` and `.view` are. (10) ` ` before a `.`, hashbang and BOM, nested template literals, numeric separators, `?.5`, class private names, ID_Start letters outside the BMP or in the letter-number category and combining marks were tokenised wrongly or not at all. (11) The storefront scan in `scripts/check-layers.mjs` stripped comments with a regex (so ` //` inside a string, a slash in a regex class or a U+2028 after a comment hid code) and matched names on the raw text (escapes); it now runs a small scanner of the same contract first (comments blanked with line numbers kept, Unicode escapes decoded in identifiers, strings and templates), and the D12 call and constructor rules match across line breaks (`x.click\n()`, `new\nMouseEvent`).

**Found by the independent review of this PR and fixed in the same PR.** (12) `of` was always read as a keyword (`const of = 4; of / fetch("x") / 3` hid the call inside a supposed regex) and an arrow function body followed by a line break was always read as an operand (a regex on the next line opened a string): `of`, `yield`, `await`, an arrow body and a `++` after a line break are now ambiguous places, read in every combination (the complete product, never a sample), with every rule run on every reading and the findings merged; an unterminated regex is read as an operator. (13) The storefront scan decodes Unicode escapes also inside text it guesses to be a regex body, because that text may really be code (a division): a wrong guess can only over-report. (14) `catch (ctx)` was not refused (the rule inspected the wrong token); `ctx` is now also refused as a destructuring target (`const [ctx] =`, `const { ctx } =`, `[ctx] =`, a for-of pattern), an import name, a for-in or for-of variable and an increment target. (15) Quadratic work on hostile input (about 20 to 40 seconds for 128 KiB): `isObjectLiteralKey`, the bracket and parenthesis matching, the markup regexes `<` plus spaces and `<[^>]*` plus popover or inert (admin and storefront scans), the regex-literal look-ahead, `$(` argument scans and several look-backs; the bracket structure is now computed once, the regexes are linear, the look-aheads are capped and the regex literal look-ahead is a one-pass table (no length cap). `tests/scan-lexer.test.mjs` pins a generous time bound.

**Second review round (same PR).** (16) A reading set that is capped is a sample, and the real reading can be a mix: a file with 23 or more ambiguous slash places hid code from every sampled reading. The set is now complete or the file is refused: up to 4 ambiguous places (at most 31 readings) are enumerated in full, and MORE than 4 in one reading is a violation of the NEW rule `js/ambiguous-slash` (message: add semicolons or parentheses so that each `/` is unambiguous). The owner approved this guard-script hardening; the rule only tightens, and the template's own code, the repository's JavaScript and the corpus below have no ambiguous place at all. (17) The 1000-character cap on a regex literal made a long valid regex an operator and its body code (a quote inside it opened a string); the look-ahead now needs no cap (a one-pass table of the closing slash per position, in the admin lexer and in the storefront scan), so a regex of any length is a regex and the work stays linear. Differential check against acorn's tokenizer on 10,760 real files (the node_modules of a large project plus this repository): zero token mismatches, none of those files has an ambiguous place.

**Tests (all in the normal suites, a few seconds).** `admin/scripts/__fixtures__/escaped-cases.mjs` generates, for every D12 category (network, storage, eval, window and document, raw HTML, dialog, popover, inert, synthetic events, DOM traversal, ctx shadowing, aliasing, imports) and every forbidden name, the plain spelling and five escaped spellings that must report the SAME rule id, the string, template and import-specifier forms with `\x`, `\u`, `\u{}` and octal, the exotic whitespace, line terminator, comment, optional chaining, parenthesis and number / regex look-alike forms, plus negative cases proving legitimate code is still accepted (run by `node admin/scripts/test-guard.mjs`); `tests/scan-lexer.test.mjs` pins the token contract and the storefront scan; `tests/scan-fuzz.test.mjs` is a seeded property test (mulberry32, default seed 0x17d17, override with `SCAN_FUZZ_SEED` and `SCAN_FUZZ_ITERATIONS`) that applies random semantics-preserving transformations to every forbidden construct (random identifier escapes, separators and comments at token boundaries, parentheses, `?.` and bracket rewrites), uses Node as the oracle (`vm.Script` for syntax, the engine's own evaluation for every escaped name and literal), and requires the scanner to report the same rules on every transformed snippet and nothing on the allowed ones. Pinned by `tests/scan-lexer.test.mjs`.

**What remains out of scope (this stays a best-effort defence, not a proof).** The scan does not parse JavaScript: it cannot follow data flow (`const f = ctx; f.x`, a name built at run time, a call through an alias of a banned function that never spells its name), it does not look inside the parts of a template literal that are split by `${}` (`<scr${""}ipt`), it does not model every grammar corner (an escaped keyword is a SyntaxError and is read by its canonical name; a `}` followed by `/` where block and object are both possible is read in every combination, see (12)), legitimate code that looks like an ambiguous place may be reported once more than expected, and the storefront scan is still a set of regular expressions over the canonical source (`(0, fetch)(x)` and `var f = fetch` are not matched by the `fetch(` rule). The real boundary is the runtime and deployment: the core never puts tokens or the network in `ctx`, the safe builder, the frozen core objects, the strict CSP, the fixed warnings in closed shadow roots, and human approval of the preview (docs/DESIGN-LAYER.md).

### D12. Guard rule tightening (design layer) and the follow-up T1-T4 plan

**Guard rule tightening, approved by the owner on 2026-11-27 ("全部照建議"), items 1-3**, under D10 (a guard-rule change is a capability-boundary change, so the owner decides). The design layer is already unable to `fetch`, touch storage or build raw HTML; these rules close the remaining ways it could take over the screen or drive a core confirmation. Enforced in two layers, because a static scan alone can be bypassed: (a) the static scan, `admin/scripts/lib/design-scan.mjs` (admin `design/` and `design-defaults/`) and section 5d of `scripts/check-layers.mjs` (storefront), and (b) RUNTIME restrictions in the core (`admin/ui/kit.js`, `admin/core/context.js`) that only take away what the design layer can do and add no `ctx` function. The current template (admin `design/`, `design-defaults/`, the storefront `public/*.js`) passes with ZERO violations; `admin/scripts/__fixtures__/cases.mjs` and `tests/guard-d12.test.mjs` hold a negative test for every construct (including each bypass the independent review found) and positive tests for the legitimate ones; `admin/e2e/d12-runtime.mjs` checks the runtime part in a real browser.
1. **Dialog, popover, fullscreen, pointer lock.** Static: rule `js/dialog-api` refuses `showModal`, `showPopover`, `hidePopover`, `togglePopover`, `requestFullscreen`, `requestPointerLock` (and the exit variants) as identifiers, and `.show(` / `.close(` as method calls (the `{ close }` argument of a dialog action is a plain function and stays allowed). `.show(` and `.close(` are ordinary method names, so the real protection is that design code can no longer create anything they act on: rule `js/dialog-element` refuses the `dialog` tag (`h("dialog")`, as a call argument or in a template) and rule `js/popover-inert` refuses the `popover` and `inert` attributes and properties. 2. **Programmatic click and auto-confirm.** Static: rule `js/synthetic-input` refuses `dispatchEvent`, `requestSubmit`, `.submit` (except `ctx.auth.passwordSetup.submit`, the core's own function), constructing `Event`, `MouseEvent`, `KeyboardEvent` and the other event classes, computed access such as `el["click"]`, and `.click` on anything except a hidden file input created in the same file with `h("input", { type: "file" })` (the upload button pattern). Rule `js/core-ui-selector` refuses strings and templates that name the core confirmation controls (`confirm-yes`, `confirm-warning`, ...). Runtime: every button of a core dialog (`showDialog`, so also `confirmDialog` and the fixed-warning confirmations) ignores events whose `isTrusted` is not true, so a synthetic `.click()` or `dispatchEvent` can never confirm; only a real user input does.
3. **Traversal out of the design's own subtree.** Static: rule `js/dom-escape` refuses `ownerDocument`, `getRootNode`, `parentNode`, `parentElement`, `offsetParent`, `composedPath`, `getElementById`, `getElementsBy*`, `elementFromPoint(s)`, sibling and `firstChild` / `lastChild` / `childNodes` / `firstElementChild` / `lastElementChild` walks, `relatedTarget` and `.view`, `.closest(` everywhere, and `querySelector` / `querySelectorAll` on anything except an element created by the same file with a `ctx.ui` builder or `root`; `ctx.ui.$` and `$$` need such an element as their second argument. Rule `js/ctx-shadow` refuses redeclaring, re-assigning or shadowing `ctx` in a nested function; `js/ctx-unknown` refuses computed access on ctx namespaces, `Object.values` / `entries` / `assign` / ... over them and spreading them. `children` (also a normal data key in the category tree) stays allowed: it only walks DOWN from an element the design owns. Runtime: `ctx.ui.$` and `$$` are scoped (they need an element root, refuse document, `html`, `body`, anything inside a dialog and any container of core UI, and never return a node inside a dialog, the toast host or the preview banner). The storefront scan does not include traversal (its event delegation uses `querySelector` / `closest` on `#app`); it covers items 1 and 2.
Known residue (accepted): the own-element and file-input exceptions are decided by names within one file, not by data flow, and the scan is a token scan, not a proof; the CSP, the core-owned confirmations, the fixed warnings, the trusted-input check and the runtime restrictions above are the real boundaries.

  merchant-owned, so every merchant gets CSP upgrades). Policy: `script-src 'self'` only (no inline scripts, no eval, no third-party
  scripts), `style-src 'self'` plus `style-src-attr 'unsafe-inline'` (the design layer sets product photos with inline `style=`
  attributes, which cannot run code), `img-src 'self' data: https:`, `connect-src 'self' https:`, `object-src 'none'`,
  `base-uri 'none'`, `frame-ancestors 'none'`, `form-action 'self'`. Known limitation: `connect-src` / `img-src` allow any `https:`
  origin because the file is identical in every repo; pinning them per merchant is a possible follow-up.
  Enforced by `scripts/check-layers.mjs` (fails when `_headers` is missing, has no CSP, or weakens it; an inline `<script>` or
  `on*=` attribute in `public/index.html` is an error in the template and a warning in a merchant repo) and exercised by the
  storefront browser test (`tests/e2e/serve-storefront.mjs` sends the real policy).
  The optional localhost override is loaded from `public/commerce/local-config.js`, not from an inline script.
* **v0.2.1 amendment (approved by the owner on 2026-11-26)**: `form-action` is `'self'` plus the two ECPay payment hosts
  (`https://payment.ecpay.com.tw`, `https://payment-stage.ecpay.com.tw`) because checkout POSTs a form to ECPay; HSTS, Permissions-Policy and
  COOP are added to `public/_headers` and `admin/deploy/nginx.conf.template`. Pinning `connect-src` / `img-src` per merchant stays a follow-up: the file is
  locked and overwritten by every sync, so per-merchant values need a design decision first (see the comments in `public/_headers`).
* **Admin**: `admin/deploy/nginx.conf.template` sends the CSP on every response and `admin/deploy/Dockerfile` installs it; it is on by
  default, there is no switch to turn it off. Enforced by `admin/scripts/check-design.mjs` (step "deploy") and tested in
  `admin/scripts/test-guard.mjs`; the design e2e (D8) runs the admin under the policy.
* **Preview environments** of the future AI edit service must serve the same policy (`admin/docs/AI-EDIT-SERVICE-NOTES.md`).
* A hosting setup outside this repo (another nginx, a CDN rule) is not checked by the guards: a human must carry the policy over.

### D2. `admin/styles.css` stays LOCKED

The admin's AI customises through `admin/design/tokens.css` and `admin/design/theme.css` only. `admin/styles.css` is core (hash
manifest); a design that needs more than tokens and theme rules escalates to a human core change.

### D3. Irreversible actions: the warning is FIXED and core-owned

The confirmation dialog of each irreversible admin action is composed of editable wording from `admin/design/copy.js`
(`confirm.<id>.title`, `confirm.<id>.text` lead-in which may be empty, the button labels) plus a **fixed warning** that lives in
`admin/core/warnings.js`, has no copy key, and is always rendered by the dialog (`data-testid="confirm-warning"`). Copy that tries to
define one (any `confirm.*.*warn*` key) is rejected by `validateCopy` (`lib/design-schema.js`) and therefore fails the guard; the
retired v0.1.0 `confirm.<id>.message` keys of the irreversible confirms are ignored (console warning and a guard note, not a failure, so
a v0.1.0 merchant can still sync and then renames them); CSS that hides the warning is rejected (`css/hides-dialog`).
Covered by `admin/scripts/test-guard.mjs`, `tests/decisions.test.mjs` and the design e2e section D7b. The storefront has no
confirm-style irreversible UI (cart line removal is a plain "REMOVE" link on a reversible, client-only bag), so nothing was added there.

### D4. Core changes and the `ctx` surface are human-reviewed

Adding a function or action to the design-layer `ctx` (or any other locked-core change) is a human-reviewed core change, written
up in `.claude/skills/core-change`. **Only a human runs a manifest `--update`** (`node scripts/check-layers.mjs --update`,
`node admin/scripts/check-design.mjs --update`); an AI session never does, and never runs `sync-core` or `new-merchant`.

### D5. Merchant repos come from `new-merchant.mjs`; syncs come from a TAG only

* Merchant repos are created with `scripts/new-merchant.mjs`. The GitHub "Use this template" button is only for finding the template.
* Core syncs are run by a human, per merchant (`.claude/skills/template-release-and-sync`).
* The sync source is a **tag only**: `sync-core.mjs` refuses a template checkout whose HEAD is not exactly at the annotated tag
  `v<template.json version>` with a clean work tree (exit 2), unless a human passes the loud `--allow-untagged` override, which is
  logged in the output and appended to the history in the merchant repo's `.template-version`.

### D6. Content schema: registration is HUMAN ONLY

`public/content.schema.json` (a storefront **design-layer** path: the AI may edit it) describes the shop's editable content for the
platform's per-shop content schema. **Editing the file registers nothing.** Registering a schema on the platform
(`PUT /api/v1/admin/shops/{id}/content/schema`) is done by a human who holds `content.manage` after reading a dry-run report; CI,
the AI edit service, deploy hooks and unattended scripts never call it. `scripts/check-content-schema.mjs` can lint the file offline
and dry-run it (`?dry_run=true`, writes nothing; credentials from environment variables only); it has no registration code path.
Since v0.3.0 the storefront reads published platform content with `content.js` as the default copy (D7) and the admin registers a schema only through the confirmation dialog (D8).
