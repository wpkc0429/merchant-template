# Decisions

Standing decisions about the merchant template and every merchant repo made from it. Each one was **decided by the user**
(the template's owner) and is enforced by the tooling named next to it; changing one is a human decision, recorded here
first. Newest first. This file is part of the locked core (it is synced to merchant repos so design sessions can read it).

## 2026-11-28, decided by the owner

### D20. Hardening PR 4 (stage A of D16): merchant-specific storefront origins, a derived `public/_headers`, the storefront network scan and the trust-boundary analysis

Approved by the owner as item "storefront connect-src / img-src tightened to merchant-specific origins via the new sync mechanism" of the stage A hardening plan (D16), **including the sync / manifest-procedure change** that mechanism needs and **the storefront scan reinforcement** that the independent reviews recommended (both guard-script changes, approved by the owner under D10). No new `ctx` or `ShopCommerce` function; the public API files are unchanged.

**The problem.** The storefront runs in the customer's browser (cart, checkout form with name, phone and address, order access token). `public/_headers` carried `connect-src 'self' https:` and `img-src 'self' data: https:`, so any `https` origin was reachable from script (`fetch`, `sendBeacon`, `WebSocket`) or from an image request: a hostile or buggy design layer could send customer data anywhere, and the static scan was the only defence. The file was locked and overwritten by every `sync-core` with the template's copy, so per-merchant origins could not be stored in it (v0.2.1 left this as a known limitation).

**The mechanism.**
1. **Core template** `scripts/headers.core.txt` (locked, synced, identical in every repo): the former `_headers` with one token per configurable directive (style, img, font, connect, frame). **Merchant config** `merchant.headers.json` at the repo root (merchant-owned, HUMAN only, never in `public/`, so never published): `apiOrigin` and `imageOrigin` (required), optional `extraConnect`, `extraImg`, `extraFont`, `extraStyle`, `extraFrame`. **Renderer** `scripts/render-headers.mjs` (locked, no dependencies, deterministic) writes `public/_headers`, which stays committed because Cloudflare reads it from the assets directory, but is **DERIVED**.
2. **Strict validation.** Every value is a bare `https` origin written exactly as the URL parser prints it (lower case, no path, query, userinfo, trailing slash or default port) with a domain name and a letter-only top-level domain: no `https:` / `*` / `data:` / `ws:` scheme source, no wildcard (not even a single-level subdomain: no case for one was shown, and a wildcard on a shared suffix would admit other tenants), no `http:` (a dev server may pass `dev: true` in code, as `tests/e2e/serve-storefront.mjs` does for its local throwaway stack; the file never may), no IP address or `localhost`, unknown keys refused, at most 5 extras for connect and img and 3 for font, style and frame, no duplicates. `script-src` stays `'self'` and `form-action` stays `'self'` plus the two ECPay hosts: neither is configurable.
3. **Rendered policy.** `connect-src 'self' <apiOrigin> <extraConnect>`, `img-src 'self' data: <imageOrigin> <extraImg>`, `font-src 'self' <extraFont>`, `style-src 'self' <extraStyle>`, `frame-src 'none'` (or the declared frames), `script-src 'self'` (no inline), `frame-ancestors 'none'`, `form-action` as before, and every header added in v0.2.1. Fonts: the storefront needs none from outside (self-hosted or system fonts), so `font-src` and `style-src` stay `'self'` unless a merchant declares `extraFont` / `extraStyle`.
4. **Guard (`scripts/check-layers.mjs`, step 5e).** `public/_headers` must be **byte-identical** to the rendering of the current core template and the merchant config (a hand edit or a stale file fails); the config is validated strictly; `checkCsp` additionally refuses a bare scheme, wildcard or `unsafe-*` source in `connect-src`, `img-src`, `font-src`, `style-src` and `frame-src`; the origin of `public/config.js` `apiBase` must be allowed by `apiOrigin` / `extraConnect`. A leftover `replace-with-*` placeholder in `merchant.headers.json` is a **warning in the template and an ERROR in a merchant repo**. `public/_headers` is no longer hashed in `scripts/commerce.manifest.json` (a manifest that still lists it is tolerated and ignored; `--update` drops it).
5. **`sync-core`.** `public/_headers` and `merchant.headers.json` are merchant-owned paths: a sync never copies the template's version of either. After the locked files (including the new core template and renderer) are copied, the sync **re-renders** `public/_headers` from the new core template and this repo's own config, so the merchant's values are preserved across syncs and never replaced by the template placeholders; if the config is invalid the whole sync is rolled back. A merchant without `merchant.headers.json` is refused before anything changes, with the migration text. **Migration (once, a human)** for a merchant created before v0.5.0: copy `merchant.headers.json` from the template, set `apiOrigin` and `imageOrigin`, run `node <template checkout>/scripts/render-headers.mjs --root . --core <template checkout>/scripts/headers.core.txt`, commit, then sync as usual (the running pre-0.5.0 `sync-core` does not know the config, which is why the file must exist first). **`new-merchant`** fills the config from `--api-base` (config.js `apiBase`) and the new `--image-origin`, renders, and re-locks; a missing `--image-origin` leaves the placeholder, which the guard reports as an ERROR until a human fills it in (its own scripted verification passes `--allow-placeholders`; CI and humans do not).
6. **Human-only.** `scripts/check-scope.mjs` already allowed only the design paths, so the config and the rendered file were out of scope for storefront and admin AI sessions; it now also has an explicit deny list (`merchant.headers.json`, `public/_headers`, `scripts/headers.core.txt`, `scripts/render-headers.mjs`) that applies even if a (hostile) `template.json` listed them as design paths. `check-locked` protects `public/_headers` and `merchant.headers.json` through `merchantOwnedPaths` and the core template and renderer through `lockedPaths`. The config is edited by a human, who then runs `node scripts/render-headers.mjs`; it needs no manifest `--update`.

**Storefront network scan (`check-layers.mjs`, step 5f).** On the canonical source (D17: comments blanked, escapes decoded) plus a **masked** view in which the text of string and template literals is blanked: `fetch`, `sendBeacon`, `WebSocket`, `EventSource` and `XMLHttpRequest` are refused as identifiers in any position (`(0, fetch)(x)`, `var f = fetch`, `navigator.sendBeacon`, `window.fetch`, destructuring), except as an object key whose value is a literal (`{ fetch: 1 }`, data); as exact string values after joining `'fe' + 'tch'` and decoding escapes (`window['fetch']`, `globalThis["\x66etch"]`, `Reflect.get(window, 'fetch')`); `new Image`, `new Audio`, `new Worker` and `new SharedWorker` (a script-created element is a request to every allowed origin); `RTCPeerConnection` (WebRTC is outside `connect-src`); `window.open`; dynamic `import()` and `import.meta`. Copy text, comments and look-alikes (`refetch`, `prefetched`, `ImageList`) pass. Core files (`public/commerce/**`, `config.js`) are not design files and stay exempt exactly as before; the template's own design files and the code blocks of the storefront-design skill produce zero findings. This is an early warning and a bypass-resistant net for the cheap cases; the pinned CSP is the actual fence.

**Trust-boundary analysis (storefront, read from the code).**
* *Loading.* Classic scripts, one realm, no bundler: `config.js`, `commerce/local-config.js`, then the core (`api.js`, `cart.js`, `content-allowlist.js`, `content.js`, `checkout.js`, which freezes `ShopCommerce`), then the design layer (`content.js`, `app.js`). Core runs first, so it can capture what it needs; `check-layers` enforces the order.
* *What lives where.* The cart (`localStorage`, key `shopcommerce:cart:<shop hash>`, hashed from the publishable key) and the order access token (`sessionStorage`, `shopcommerce:orderAccessToken` and `...:orderId`) are written and read only by the core; the platform content cache and the content preview token (taken out of the URL at once, kept in a closure) likewise. The customer's checkout form values (name, phone, address, email) live in `state` in `app.js`, i.e. in the design layer: the design layer renders the form, so **it necessarily holds the customer's personal data**. There is no customer account session on the storefront.
* *Leaks that were reachable from the design layer at runtime* and are **fixed here** (cheap, design-layer-only, no public API change): (1) `ShopCommerce._internal` (`apiFetch`, which adds the publishable key and bearer tokens and accepts any path and header, the config and the image-origin registry) was an enumerable property of the global; `checkout.js`, the last core script, now removes it after the earlier scripts took what they need into closures, so design code (or a scan bypass) can no longer call `apiFetch`; (2) `window.SHOP_CONFIG` was a mutable object the core read on every request (`apiBase`, `publishableKey`), so design code could repoint the API client; it is now frozen after the core loads (`local-config.js` runs earlier and is unaffected). Both are tested in the sandbox (`tests/storefront-origins.test.mjs`) and by the storefront e2e.
* *Not fixed, by design or too large for this PR (recommended follow-ups).* (a) `getOrderToken()` and `placeOrder()` hand the **order access token** to the design layer, which passes it to `startPayment(token)`; a core-held token (no token in the API, `startPayment()` and `loadOrderStatus()` read it internally) would remove the last secret from the design layer. It changes `public-api.json`, so it is a design-layer action: its own PR. (b) The checkout form and its values stay in `app.js`; moving the fields into a core-rendered component would be a redesign. (c) Freezing the JavaScript intrinsics (as D18 does for the admin) is not done for the storefront: `Object.prototype` and `Array.prototype` freezing breaks ordinary assignment patterns in third-party-style design code (the override mistake) and, because the design layer already holds the data it could leak, it does not change what egress is possible; the CSP and the scan do. Hooks on `Storage.prototype`, `JSON` or `Promise` can only observe data that design code can read anyway.
* *The decisive control is egress.* With `connect-src` pinned to the merchant's API origin and `img-src` to its image origin, the remaining channels are: requests to the API origin itself (placing orders on the platform is what the storefront does), the image origin (read-only host), **top-level navigation** (`location.href`, `<a href>`, `<meta refresh>`, `window.open`: no CSP directive governs it, `navigate-to` was never shipped; the scan refuses `window.open` but navigation is also what the design layer legitimately uses, so it is not scanned), WebRTC (scanned), DNS prefetch and similar browser hints, and the `form-action` ECPay hosts (a form can only POST to them). These are the residual risks.

**Residual risks, stated plainly.** (1) A design layer that is hostile or buggy and that defeats the scan can still read the customer's data (it renders it) and can leave the page by navigation or hand data to the platform API; the CSP makes the quiet channels (fetch, beacon, socket, image ping, form post) end at the merchant's own two origins. (2) The merchant config is a human responsibility: a careless `extraConnect` widens egress; the guard limits the count and shape, not the trust in the host. (3) `merchant.headers.json` must match what the platform really serves: an image host that differs from `imageOrigin` blocks the product photos (the browser test shows it as a CSP violation); product image URLs come from the API, so a platform move of its image host needs a config change. (4) Cloudflare reads `public/_headers` at deploy; a deployment that does not serve it (another host, a preview service) must carry the same policy over (D1). (5) The scan is a heuristic net on the canonical text; aliasing through computed template-literal names or closures built from data it cannot see is not caught, which is why the CSP is the fence. (6) A merchant that migrates late keeps the pre-0.5.0 `https:` policy until it syncs.

Covered by `tests/storefront-origins.test.mjs` (renderer, validation, derived-file and placeholder guard, scope and locked-path refusals, sync preservation, rollback and migration, new-merchant, the scan fixtures with positives and negatives, the runtime handle and freeze check, this record), the updated `tests/decisions.test.mjs`, `tests/guard-d12.test.mjs`, `tests/scan-lexer.test.mjs`, `tests/content-guards.test.mjs`, `tests/sync-core.test.mjs`, `tests/new-merchant.test.mjs`, and the storefront browser tests, which now serve the policy rendered from `scripts/headers.core.txt` (`tests/e2e/serve-storefront.mjs`) and assert that a request to another https origin is blocked.

### D19. Hardening PR 3 (stage A of D16): import-map isolation of design modules, fail-closed canary, boot-phase seals, and the approved guard CSP rule change

Approved by the owner on 2026-11-28 ("好") as item 3 of the stage A hardening plan, **including an explicit change of a GUARD RULE** (under D10 a guard change needs the owner): the CSP checks of `admin/scripts/check-design.mjs` (`cspProblems` for the server level and every location, and `deployChecks`) used to force `script-src` to be exactly `'self'`. They now allow ONE extra token, the `'sha256-...'` of the exact text of the inline import map in `admin/index.html`, and nothing else. **No new ctx function, no other guard rule, no new scan rule.** There is no equivalent check in `admin/scripts/check-layers.mjs` (it only forbids inline scripts in `config-loader.js`, `config.js` and `index.html` by the pattern `<script>`, which an `importmap` script does not match); the storefront's `scripts/check-layers.mjs` and `public/_headers` are untouched.

**The problem.** Design modules are same-realm, same-origin ES modules loaded by `lib/design.js` with `import()`. The static scan lets them import only relative paths inside `design/`. If the scan is ever bypassed, a hostile module could import the core modules whose closures hold the sealed API client (`lib/orders.js`, `lib/catalog.js`, `lib/content.js` with `putSchema`, `lib/design-review.js` with `approveRequest`, `core/*`, `ui/kit.js`, ...) and use them without the ctx permission checks and confirmations.

**The design.**
1. **Import map** (`admin/index.html`): one inline `<script type="importmap">` on ONE line, before every module script. Scope `/design/`: `"/"`, `"https://"` and `"http://"` go to `/deny/`, `"/design/"` goes to itself. So every module whose URL is under `/design/` can import files under `/design/` only (the design's legitimate set: its own `views/`, `parts/`, `copy.js`, `routes.js`; the scan never allowed more, and `design-defaults/` is imported only by the core). Everything else is sent to `/deny/<path>`, a core-owned URL that answers 404 (`location ^~ /deny/ { return 404; }` in `deploy/nginx.conf.template`; the dev server has no such file), so the import rejects with a TypeError (not `null`, which only warns). The core's own imports (referrer outside the scope) are unaffected. Spellings tested: relative, absolute path, absolute URL, protocol-relative, query string, percent-encoding, `/design/../lib`, dot segments, backslashes, `new URL(..., import.meta.url)`, `data:`, bare, `blob:`, dynamic `import()` with computed specifiers.
2. **Hash mechanism.** Without a CSP hash the browser blocks the inline map and IGNORES it (fail-open), so `script-src` carries `'sha256-<hash of the exact map text>'`. The template has no build step: the hash is a static value in `deploy/nginx.conf.template` (the server CSP and the `/site-config.js` location), verified by the guard on every run (`deploy` step: it recomputes the hash from `index.html` and requires `script-src` to be exactly `'self' 'sha256-<that hash>'`, order tolerant, in the server CSP and in every location that repeats it; any other token (`'unsafe-inline'`, `'unsafe-eval'`, another or a second hash, a nonce, a host, a scheme, `'strict-dynamic'`, `'unsafe-hashes'`, a hash or nonce in any other directive) is `deploy/csp-weak`; `index.html` must have exactly ONE inline script and it must be the import map: rule `deploy/importmap`); the HTML is read by a small tokenizer (comments including `<!-->`, quoted attributes, `data-src` is not `src`), no new rule id. The documented `node scripts/check-design.mjs --update` (human, locked-file flow) now also rewrites the hash in the nginx template after the map changed. The map is one line so CRLF checkouts hash the same.
3. **Fail-closed canary.** `lib/canary/probe.js` (core-locked in `lib/`: a design file cannot be core-owned, so the probe sits outside `design/`) lives in its own DIRECTORY scope, `/lib/canary/`, built like the design scope (same keys: `"/"`, `"https://"` and `"http://"` denied, one allowed prefix, `/lib/canary/allowed/`, mapped to itself), so it exercises a prefix scope of the same kind as the real wall. `app.js` runs it after the seal and the freeze and BEFORE any design module is imported. It checks `HTMLScriptElement.supports("importmap")`, imports a positive control (`lib/canary/allowed/ok.js`, must load), then FETCHES `lib/canary/target.js` (fetch is not subject to import maps; it must answer 200 with a JavaScript content type, else the check reports `unverifiable` and fails closed: a refused import of an unreachable file proves nothing) and finally imports it (must be denied). Only "fetch succeeded AND the import was denied" counts as isolated. If the target RESOLVES (map not in effect: hash missing, unsupported or old browser, map text changed or removed), is unreachable, or the control fails, the design layer is NOT loaded: `loadDesign({ enabled: false })` imports nothing from `design/` and stays off for good, the built-in screens and copy are used, the console warns `[design] custom design is DISABLED ...` with the reason, and the owner sees one calm core-drawn note (`iso.disabled`). The design CSS (`tokens.css`, `theme.css`) stays, being plain `<link>` files that cannot run code.
4. **Boot-phase seals** (defence in depth, same pattern as `takeApi()`; new `lib/boot.js`, closed by `sealApi()`): `lib/perm.js` (`takePermissions`: setPermissions, clearPermissions), `lib/session.js` (`takeSession`: the mutable state, loadSession, login, logout, clearSession, passwordSetup, invitations; the exported `session` is a frozen read-only view and its `user` object is frozen), `core/auth.js` (`takeMakeAuth`), `core/design-actions.js` (`takeDesignActions`), `core/content-actions.js` (`takeContentActions`), `ui/kit.js` (`takeCoreUi`: showCoreDialog, confirmDialog, allowImageOrigin, allowPreviewLinkOrigin). The old named exports are gone. Core behaviour is identical; the offline test scripts call the `take...()` functions (the boot phase is open there). `loadDesign` cannot be called again to switch a disabled design layer on.
5. **nginx**: `location ^~ /deny/ { return 404; }` and, at server level before every location, `if ($request_uri ~* "^[^?]*(%2f|%5c|%2e|//)") { return 404; }`: any request whose PATH (not the query) holds an encoded slash, backslash or dot, or a double slash, is refused for the whole admin. nginx DECODES and MERGES those while the browser's import map only sees the URL as written: `/design/..%2flib/orders.js` would be a fresh copy of a core module, and `/design%2fcopy.js` and `//design/copy.js` serve `design/copy.js` for a URL outside the `/design/` scope (found by the independent review, checked against real nginx 1.27; the browser test shows the first with an emulated decoder). No published file name has such characters (letters, digits and `. _ -` only). The template was also run by hand in nginx:1.27-alpine (`nginx -t` passes; the paths above, `/deny/...` and `/design/..%5clib/...` answer 404; `/design/copy.js`, `/lib/canary/allowed/ok.js`, `/site-config.js` and a query string holding `//` or `%2f` answer 200; the CSP header carries the hash); that check is not part of the automated suites.

**Limits, stated plainly.** (a) **This is not isolation.** A same-origin module can still read the DOM, call anything `ctx` hands out, and call the platform's cookie refresh endpoint itself; `fetch` is banned only statically. A module that obtains a Worker (banned statically; `worker-src` has `blob:`) runs outside the import map. Real isolation (sandboxed iframe or worker, or a DSL) stays POSTPONED (D16, options B, C, D). (b) The wall depends on the server: a server that redirects a URL under `/design/` to a core file gives that file's final URL outside the scope (a redirect to `lib/orders.js` is refused only because a fresh copy of a boot-phase module throws at evaluation; a redirect to a module without a `take...()`, e.g. `lib/dates.js`, resolves). nginx has no such redirect and the guard refuses symlinks in `design/`. (c) Scopes use absolute paths, so the admin must be served at the origin root (it is). (d) The canary tests the probe's scope, not the design scope: a deployment whose map text is valid and hash-matched but has lost the `/design/` scope would pass the canary; the browser test and `tests/import-map-isolation.test.mjs` assert the shipped map's structure. (e) **Firefox and Safari are NOT verified** (only Chromium was run). Import maps with scopes and CSP hashes are standard, but nothing here claims they behave identically; the canary is the fail-closed mechanism: a browser that does not enforce the map turns the custom design OFF instead of leaving it unprotected. Verify them before relying on custom designs there. (f) Not sealed by name (the map is their wall): `lib/orders.js`, `lib/catalog.js`, `lib/content.js`, `lib/design-review.js`, `lib/design-history.js`, `lib/members.js`, `lib/team.js`, `lib/upload.js` and the other data modules, which hold the boot-phase client in their closures. (g) The start-up probe makes the browser log one 404 for `/deny/lib/canary/target.js` in the console on every load; the browser suites ignore exactly that URL.

**Preview hosts and the future AI-edit service.** Every host that serves the admin files (production, preview hosts, the service's preview environments) MUST serve the same CSP with the hash AND the `/deny/` 404 AND the `%` refusal, i.e. the same image. A host that lacks the hash is not broken for the owner: the canary turns the design layer off there, so a preview that "does not show my design" means the CSP or the map is wrong. After a change to the map in `index.html` a human runs `--update`; the service must not touch `index.html`, `deploy/` or `lib/`.

Covered by `admin/e2e/import-map.mjs` (real Chromium, the real CSP read from the nginx template, fake API recording Authorization headers; control runs with the map removed and the canary bypassed, and with an nginx-style decoder and no percent rule, prove the tests can fail), the guard negative tests in `admin/scripts/test-guard.mjs`, `tests/import-map-isolation.test.mjs`, and the updated suites (`hardening`, `design-history`, `design-review`, `design`, `d12-runtime`, which now serve the CSP with the hash).

### D18. Hardening PR 2 (stage A of D16): sealed API, frozen intrinsics, preview host, delayed approve, scan report

Approved by the owner on 2026-11-27 as items of the stage A hardening plan (D16 (c)): "token / refresh not importable and frozen intrinsics", "1-second delayed enable of the approve button", "the scan report shown to the approver", and the template side of the platform's server-enforced read-only preview sessions. These are CORE changes that only RESTRICT the design layer: **no new ctx function, no guard script rule change, no CSP change**, and the template's own design code needed no change. Reviewed independently like the other core changes (D10). The first independent review of this PR led to the follow-up described in item 6.

1. **Sealed API capability.** `lib/api.js` keeps the authenticated client, the access token and the refresh logic in its closure. There is no `tokens` export and no `.access` getter. The only ways in are `takeApi()`, which works **only during the boot phase** (every core module calls it once at evaluation: the `lib/*` data modules, `lib/session.js`, `core/auth.js`, `app.js`), and `sealApi()`, which `app.js` calls first thing in `boot()`, after every core module was evaluated (the core has no lazy imports) and before the design layer is imported (`lib/design.js` is the only importer). After that `takeApi()` throws, so a module imported later cannot obtain the client, a token, refresh, login or the unauthorized hook. `lib/api.js` exports only `ApiError`, `takeApi` and `sealApi`; `lib/session.js` no longer re-exports `restoreSession`; `session` holds no token. The offline suites sign in through the boot-phase client (`admin/scripts/lib/test-signin.mjs`). `lib/upload.js` freezes `heicHooks` at seal time and takes the vendored decoder function out of `window` the moment its script ran (a `window.heic2any` that already exists is refused).
2. **Frozen intrinsics.** `lib/lockdown.js` (`lockdownIntrinsics()`, called by `app.js` right after the seal and before the design layer loads) **enumerates every own property of the global object** instead of keeping a list of names (see item 6), and freezes among others the language intrinsics and prototypes (Object, Function, Array, String, Number, Boolean, Symbol, BigInt, Date, RegExp, Error and its subclasses, Promise with its statics, Map, Set, WeakMap, WeakSet, typed arrays, ArrayBuffer, DataView, the iterator, generator and async prototypes, JSON, Reflect, Math, Intl, WebAssembly), the web platform classes the core's data passes through (Headers, Request, Response, URL, URLSearchParams, FormData, Blob, File, AbortController, EventTarget, Event and the event classes, Node, Element, every HTML and SVG element interface, Document, DocumentFragment, XMLHttpRequest and its upload, Storage, TextEncoder, TextDecoder, DOMParser, observers, canvas contexts, ImageBitmap and more), `window.ADMIN_CONFIG`, and makes `fetch`, `XMLHttpRequest`, `Promise`, `JSON`, `structuredClone`, `queueMicrotask`, `setTimeout` and the other listed bindings non-writable and non-configurable on `window`. The "override mistake" (`error.name = "X"` on an instance of a frozen prototype throws) is avoided for the few well-known keys (`Object.prototype.constructor / toString / toLocaleString / valueOf`, `Error.prototype.name / message / toString` and the subclasses, `Function.prototype.constructor / toString`, `Array.prototype.constructor / toString / toLocaleString`) by turning those data properties into accessors whose setter creates an own property on the instance (assigning on the prototype itself still throws); the core's error classes and the vendored decoder rely on that. Nothing the core itself needs to patch later is frozen (the core patches nothing). Strict-mode attempts throw; sloppy-mode attempts have no effect.
3. **Preview host (template side).** The platform enforces read-only on the server for sessions issued to a registered preview origin (`ADMIN_PREVIEW_ORIGINS` on the platform; scope `preview_ro`, cookie `__Secure-admin_preview_refresh`, 30 minutes maximum). The client read-only flags stay UX only. A preview host (`ADMIN_PREVIEW_MODE` set) now **accepts only a session whose login or refresh answer says `scope: "preview_ro"`**; anything else is dropped at once with a calm explanation (`preview_scope_missing`: the host is not registered as a preview origin on the platform). A 403 `preview_read_only` is shown as the fixed message "this is a preview, go back to the normal admin to edit" and never probes `/admin/me` or logs the person out. When the preview session ends (the refresh is refused) the login screen shows a preview-specific notice. Tokens live in memory per origin, so nothing is shared between the preview and the normal origin.
4. **Approve delay.** In the review dialog the approve button (and the reject confirmation, the only other irreversible one) stays disabled until the person ticked the box with a real click **and** 1 second passed since the dialog (or the panel) appeared; a visible countdown says why. Cancel, close and back are never delayed.
5. **Scan report to the approver.** The service-claims region of the review dialog shows the guard verdict with the rule ids and the violation count, the sha the guard checked next to the sha to be approved (a warning when they differ), the guard version and time, the number of changed files and the full list of changed paths (collapsed, one click), and the wording that the guard is run by the service and is not verified by the platform. All texts are core-owned fixed zh-TW text with no copy key.

6. **Follow-up after the independent review (same PR).** (a) The freeze is now an enumeration, not a blacklist: every constructor on the global object is frozen with its prototype and parent classes (so `ShadowRoot.prototype.adoptedStyleSheets`, which receives the core's CLOSED root as `this`, and the classes a list would forget, such as `FileList`, `DataTransfer`, `PerformanceObserver`, `CustomElementRegistry`, `Notification`, `Temporal` where it exists, are covered), every namespace-like object is frozen with the classes inside it, and every global binding (`getComputedStyle`, `matchMedia`, `open`, `requestAnimationFrame`, `setTimeout`, ...) becomes non-writable and non-configurable. The explicit exceptions are `EXCEPTIONS` in `lib/lockdown.js` (`heic2any`, whose script assigns it on first use, and names starting with `__`, the test hooks); the real-browser test enumerates the globals again and fails when anything else is left open, so a new browser API cannot silently stay unfrozen. (g) **Window accessors.** The enumeration covers data properties; the configurable ACCESSOR properties of the global object (`innerWidth`, `innerHeight`, `devicePixelRatio`, `scrollX`, `visualViewport`, `name`, `opener`, `sessionStorage`, the `on*` handlers, ...) were still redefinable (`Object.defineProperty(window, "innerWidth", { value: 99999 })` worked in Chromium) and the dialog-in-viewport check and the preview banner geometry read `innerWidth` / `innerHeight`. Known exception: the named-properties object above `Window.prototype` (WindowProperties) cannot be frozen, a browser special case (low risk: it only answers for names that are not otherwise defined). (f) **A failed guard does not block approval, by design**: the scan report is a service claim shown to the human (D13, D14), not a gate; `passed: false` is displayed prominently with the rule ids but the person may still approve. Blocking would make the platform trust a verdict it cannot verify, and the human, not the guard, is the approval authority.

The freeze closes poisoning of built-ins, not abuse of the capabilities `ctx` legitimately hands out. ### D17. Hardening PR 1 (stage A of D16): the design scans compare canonical values, not spellings

Approved by the owner on 2026-11-27 as the first item of the stage A hardening plan (D16 (c)); the owner explicitly approved the fix to the guard scripts for this item (under D10 a guard change otherwise needs the owner). This is a DEFENSIVE bug fix of our own static scanner, found by a static review that suspected the hand-written lexer did not normalise Unicode escapes: it did not, and the review of every rule that reads token text found the rest of the gaps below. **No new ctx function, no new rule id, no CSP change, no runtime change, no allow-list widened**; the template's own design code (`admin/design`, `admin/design-defaults`, the storefront paths) still produces zero violations. Reviewed independently like the other core changes (D10).

**The contract (also the first comment of the lexer in `admin/scripts/lib/design-scan.mjs` and the section "How the scan reads your code" of `admin/docs/DESIGN-LAYER.md`).** Every rule compares CANONICAL values: an identifier or property name by its escape-decoded value (`\uXXXX` and `\u{...}` anywhere in the name; non-ASCII ID_Start / ID_Continue characters, ZWNJ and ZWJ belong to a name; no Unicode normalisation, as JavaScript compares code points; `#private` names too); a string literal and a template literal chunk by their COOKED value (`\xHH`, `\uXXXX`, `\u{...}`, legacy octal, `\0`, the single-character escapes, line continuations, identity escapes); line terminators are `\n`, `\r`, `\r\n`, U+2028 and U+2029 everywhere (they end a `//` comment and an unterminated string, and count lines); whitespace is whatever `\s` covers (NBSP, BOM, the Zs spaces). `lex()` keeps `raw` next to the canonical `v` for messages.

**What was found and fixed.** (1) Identifier escapes were not decoded at all: `\u0066etch(...)`, `window.local\u0053torage` and every other banned name, ctx alias and `ctx` shadow spelled with an escape passed the scan. (2) Template literals kept their raw text, so cooked values (`confirm-\x79es`, `<scr\x69pt>`, `<dialog>`) escaped every template rule; string cooking mishandled `\u{...}` without a closing brace (an endless loop in the scan), `\x`/`\u` with bad digits, a `\0` (turned into a question mark), legacy octal escapes and line continuations. (3) A number token swallowed a following property: `1..constructor.constructor("code")()` hid `constructor`. (4) A `//` comment ended only at `\n`, so code after U+2028, U+2029 or a lone CR was hidden. (5) A `/` after `)`, `}` or `]` was always read as a division, so a regex literal in statement position (`if (x) /'/.test(y); fetch(1)`) started a "string" that swallowed the rest of the line; the lexer now tracks parenthesis kinds (`if`, `while`, `for`, `with`, `switch`, `catch`) and whether a `}` ends a block, an object, a function or a class expression, and where that cannot be known (a `}` that may end a block or an object literal, followed by `/`) it lexes both readings (more in (12)) and every rule runs on all of them; an unterminated regex is read as an operator, never as the rest of the line. (6) `a?.[x + y]`, `5[x + y]`, `/re/[x + y]`, a closed template or an object literal followed by `[` were not treated as computed member access, so `js/computed-access` did not apply. (7) Compound assignments (`ctx &&= other`, `||=`, `??=`, `**=`, `>>>=`) were lexed as two tokens, so assigning to `ctx` through them was not `js/ctx-shadow`. (8) A call was only recognised when `(` followed the name directly: `(setTimeout)("code")`, `(0, x.show)()` and `x.show?.()` evaded `js/timer-string` and `js/dialog-api`; `Object?.values(ctx)` and `Object["values"](ctx)` evaded `js/ctx-unknown`. (9) String keys: `el["popoverTargetElement"]`, `el["onclick"] = fn` and `ev["view"]` were not flagged although `.popoverTargetElement`, `.onclick =` and `.view` are. (10) ` ` before a `.`, hashbang and BOM, nested template literals, numeric separators, `?.5`, class private names, ID_Start letters outside the BMP or in the letter-number category and combining marks were tokenised wrongly or not at all. (11) The storefront scan in `scripts/check-layers.mjs` stripped comments with a regex (so ` //` inside a string, a slash in a regex class or a U+2028 after a comment hid code) and matched names on the raw text (escapes); it now runs a small scanner of the same contract first (comments blanked with line numbers kept, Unicode escapes decoded in identifiers, strings and templates), and the D12 call and constructor rules match across line breaks (`x.click\n()`, `new\nMouseEvent`).

**Found by the independent review of this PR and fixed in the same PR.** (12) `of` was always read as a keyword (`const of = 4; of / fetch("x") / 3` hid the call inside a supposed regex) and an arrow function body followed by a line break was always read as an operand (a regex on the next line opened a string): `of`, `yield`, `await`, an arrow body and a `++` after a line break are now ambiguous places, read in every combination (the complete product, never a sample), with every rule run on every reading and the findings merged; an unterminated regex is read as an operator. (13) The storefront scan decodes Unicode escapes also inside text it guesses to be a regex body, because that text may really be code (a division): a wrong guess can only over-report. (14) `catch (ctx)` was not refused (the rule inspected the wrong token); `ctx` is now also refused as a destructuring target (`const [ctx] =`, `const { ctx } =`, `[ctx] =`, a for-of pattern), an import name, a for-in or for-of variable and an increment target. (15) Quadratic work on hostile input (about 20 to 40 seconds for 128 KiB): `isObjectLiteralKey`, the bracket and parenthesis matching, the markup regexes `<` plus spaces and `<[^>]*` plus popover or inert (admin and storefront scans), the regex-literal look-ahead, `$(` argument scans and several look-backs; the bracket structure is now computed once, the regexes are linear, the look-aheads are capped and the regex literal look-ahead is a one-pass table (no length cap). `tests/scan-lexer.test.mjs` pins a generous time bound.

**Second review round (same PR).** (16) A reading set that is capped is a sample, and the real reading can be a mix: a file with 23 or more ambiguous slash places hid code from every sampled reading. The set is now complete or the file is refused: up to 4 ambiguous places (at most 31 readings) are enumerated in full, and MORE than 4 in one reading is a violation of the NEW rule `js/ambiguous-slash` (message: add semicolons or parentheses so that each `/` is unambiguous). The owner approved this guard-script hardening; the rule only tightens, and the template's own code, the repository's JavaScript and the corpus below have no ambiguous place at all. (17) The 1000-character cap on a regex literal made a long valid regex an operator and its body code (a quote inside it opened a string); the look-ahead now needs no cap (a one-pass table of the closing slash per position, in the admin lexer and in the storefront scan), so a regex of any length is a regex and the work stays linear. Differential check against acorn's tokenizer on 10,760 real files (the node_modules of a large project plus this repository): zero token mismatches, none of those files has an ambiguous place.

**Tests (all in the normal suites, a few seconds).** `admin/scripts/__fixtures__/escaped-cases.mjs` generates, for every D12 category (network, storage, eval, window and document, raw HTML, dialog, popover, inert, synthetic events, DOM traversal, ctx shadowing, aliasing, imports) and every forbidden name, the plain spelling and five escaped spellings that must report the SAME rule id, the string, template and import-specifier forms with `\x`, `\u`, `\u{}` and octal, the exotic whitespace, line terminator, comment, optional chaining, parenthesis and number / regex look-alike forms, plus negative cases proving legitimate code is still accepted (run by `node admin/scripts/test-guard.mjs`); `tests/scan-lexer.test.mjs` pins the token contract and the storefront scan; `tests/scan-fuzz.test.mjs` is a seeded property test (mulberry32, default seed 0x17d17, override with `SCAN_FUZZ_SEED` and `SCAN_FUZZ_ITERATIONS`) that applies random semantics-preserving transformations to every forbidden construct (random identifier escapes, separators and comments at token boundaries, parentheses, `?.` and bracket rewrites), uses Node as the oracle (`vm.Script` for syntax, the engine's own evaluation for every escaped name and literal), and requires the scanner to report the same rules on every transformed snippet and nothing on the allowed ones. Pinned by `tests/scan-lexer.test.mjs`.

**What remains out of scope (this stays a best-effort defence, not a proof).** The scan does not parse JavaScript: it cannot follow data flow (`const f = ctx; f.x`, a name built at run time, a call through an alias of a banned function that never spells its name), it does not look inside the parts of a template literal that are split by `${}` (`<scr${""}ipt`), it does not model every grammar corner (an escaped keyword is a SyntaxError and is read by its canonical name; a `}` followed by `/` where block and object are both possible is read in every combination, see (12)), legitimate code that looks like an ambiguous place may be reported once more than expected, and the storefront scan is still a set of regular expressions over the canonical source (`(0, fetch)(x)` and `var f = fetch` are not matched by the `fetch(` rule). The real boundary is the runtime and deployment: the core never puts tokens or the network in `ctx`, the safe builder, the frozen core objects, the strict CSP, the fixed warnings in closed shadow roots, and human approval of the preview (docs/DESIGN-LAYER.md).

### D12. Guard rule tightening (design layer) and the follow-up T1-T4 plan

**Guard rule tightening, approved by the owner on 2026-11-27 ("全部照建議"), items 1-3**, under D10 (a guard-rule change is a capability-boundary change, so the owner decides). The design layer is already unable to `fetch`, touch storage or build raw HTML; these rules close the remaining ways it could take over the screen or drive a core confirmation. Enforced in two layers, because a static scan alone can be bypassed: (a) the static scan, `admin/scripts/lib/design-scan.mjs` (admin `design/` and `design-defaults/`) and section 5d of `scripts/check-layers.mjs` (storefront), and (b) RUNTIME restrictions in the core (`admin/ui/kit.js`, `admin/core/context.js`) that only take away what the design layer can do and add no `ctx` function. The current template (admin `design/`, `design-defaults/`, the storefront `public/*.js`) passes with ZERO violations; `admin/scripts/__fixtures__/cases.mjs` and `tests/guard-d12.test.mjs` hold a negative test for every construct (including each bypass the independent review found) and positive tests for the legitimate ones; `admin/e2e/d12-runtime.mjs` checks the runtime part in a real browser.
1. **Dialog, popover, fullscreen, pointer lock.** Static: rule `js/dialog-api` refuses `showModal`, `showPopover`, `hidePopover`, `togglePopover`, `requestFullscreen`, `requestPointerLock` (and the exit variants) as identifiers, and `.show(` / `.close(` as method calls (the `{ close }` argument of a dialog action is a plain function and stays allowed). `.show(` and `.close(` are ordinary method names, so the real protection is that design code can no longer create anything they act on: rule `js/dialog-element` refuses the `dialog` tag (`h("dialog")`, as a call argument or in a template) and rule `js/popover-inert` refuses the `popover` and `inert` attributes and properties. Runtime: `h()` throws a `DesignError` for the `dialog` tag (any case, any computed string, non-string tags) and for the attributes `popover`, `popovertarget`, `popovertargetaction`, `inert`, `commandfor`, `command`, `interestfor`; the view then fails to mount and the core shows the built-in view. Only the core creates dialogs (`document.createElement` inside `showDialog`). `ctx.ui.showDialog` returns only `{ close }` to the design layer, no element. Plain `position: fixed` / `z-index` CSS stays allowed.
2. **Programmatic click and auto-confirm.** Static: rule `js/synthetic-input` refuses `dispatchEvent`, `requestSubmit`, `.submit` (except `ctx.auth.passwordSetup.submit`, the core's own function), constructing `Event`, `MouseEvent`, `KeyboardEvent` and the other event classes, computed access such as `el["click"]`, and `.click` on anything except a hidden file input created in the same file with `h("input", { type: "file" })` (the upload button pattern). Rule `js/core-ui-selector` refuses strings and templates that name the core confirmation controls (`confirm-yes`, `confirm-warning`, ...). Runtime: every button of a core dialog (`showDialog`, so also `confirmDialog` and the fixed-warning confirmations) ignores events whose `isTrusted` is not true, so a synthetic `.click()` or `dispatchEvent` can never confirm; only a real user input does.
3. **Traversal out of the design's own subtree.** Static: rule `js/dom-escape` refuses `ownerDocument`, `getRootNode`, `parentNode`, `parentElement`, `offsetParent`, `composedPath`, `getElementById`, `getElementsBy*`, `elementFromPoint(s)`, sibling and `firstChild` / `lastChild` / `childNodes` / `firstElementChild` / `lastElementChild` walks, `relatedTarget` and `.view`, `.closest(` everywhere, and `querySelector` / `querySelectorAll` on anything except an element created by the same file with a `ctx.ui` builder or `root`; `ctx.ui.$` and `$$` need such an element as their second argument. Rule `js/ctx-shadow` refuses redeclaring, re-assigning or shadowing `ctx` in a nested function; `js/ctx-unknown` refuses computed access on ctx namespaces, `Object.values` / `entries` / `assign` / ... over them and spreading them. `children` (also a normal data key in the category tree) stays allowed: it only walks DOWN from an element the design owns. Runtime: `ctx.ui.$` and `$$` are scoped (they need an element root, refuse document, `html`, `body`, anything inside a dialog and any container of core UI, and never return a node inside a dialog, the toast host or the preview banner). The storefront scan does not include traversal (its event delegation uses `querySelector` / `closest` on `#app`); it covers items 1 and 2.
Known residue (accepted): the own-element and file-input exceptions are decided by names within one file, not by data flow, and the scan is a token scan, not a proof; the CSP, the core-owned confirmations, the fixed warnings, the trusted-input check and the runtime restrictions above are the real boundaries.
