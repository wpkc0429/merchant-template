# Core changelog

Versioned changes to the LOCKED core of the merchant template (`template.json` `lockedPaths`). Merchant repos receive
them through `node scripts/sync-core.mjs` (run by a human, never by an AI session). `sync-core` reads this file from the
incoming template and prints every section newer than the merchant's current version.

Format rules (the sync script parses them):

* One `## vX.Y.Z` heading per version, newest first, followed by free text.
* A line starting with `Design-layer action:` (optionally after `-` or `*`) means the merchant's DESIGN layer may need
  to change to adopt or survive this core version (a new `ShopCommerce` function, a new `SHOP_CONFIG` key, a new or
  removed admin `ctx` function, a new copy key, a renamed or removed name). `sync-core` then refuses to apply the sync
  until the human passes `--ack-design-actions`. Write `Design-layer action: none` (or omit the line) when no action
  is needed. Additions to the two `public-api.json` files are also detected automatically.

## v0.5.1 (UNRELEASED, not tagged, `template.json` stays 0.5.0 until the release)

Follow-ups of D23 (decision D24 in docs/DECISIONS.md, owner-approved; GUARD RULE changes, independently reviewed; human-reviewed core change; both manifests re-locked with the documented `--update` commands on the branch `core/followups-v0.5.1`). (1) Real HTML tokenizer for the `index.html` scans (new `scripts/lib/html-scan.mjs`, identical copy in `admin/scripts/lib/`, used by `admin/scripts/check-design.mjs` and `scripts/check-layers.mjs`): `<!--` inside `<style>`, `<title>`, `<textarea>`, `<noscript>`, `<xmp>`, `<iframe>`, `<noembed>`, `<noframes>` or a `<script src>` is no longer treated as a comment, so the D23 documented bypass `<style><!-- </style><script>evil()</script> --></style>` is refused; script data escaped and double escaped states, `--!>`, `<!-->` and `<!--->` follow the HTML standard. Checked against Chromium over a generated corpus (`tests/e2e/html-scan-differential.mjs`, also run in CI). New refusal: an `<svg>`, `<math>`, `<select>` or `<frameset>` start tag in `index.html` (the scan does not model how a browser parses the text after them): an error in the admin check and in the template, a warning in a merchant repo; the real `admin/index.html` and `public/index.html` have none. (2) The storefront network scan (`scripts/check-layers.mjs` 5f) knows the SCOPE of a local declaration: a parameter, `catch` binding, block or loop variable named `top`, `self`, `parent`, `location` or `history` exempts only the code it covers, no longer the whole file (closes the D23 residual a); no change for code that really declares the name where it uses it (0 differences on the real `bouquet` and `bouquet-next` storefront design files). (3) e2e: the admin home screen fills its stat cards in fixed slots (today, unshipped, low stock, products, shipping) instead of in the order the requests finish (`admin/design-defaults/views/home.js`, copied to `admin/design/views/home.js`); the e2e "search by order number" step looks through the pages (on a fresh database the order number also occurs in other orders' phone numbers, so the order can be on page 2: a test assumption, not a slow query); the canary's expected 404 is counted per document load from the navigation requests instead of the `load` event (a race, reproduced). No `ctx`, `ShopCommerce`, route or CSP change. Known limits: the tokenizer does not model foreign content, `<select>` or `<frameset>` (refused instead); D23 residuals b to d of the storefront scan (indirect access, incomplete aliasing) remain; the strict CSP is the real defence.

Design-layer action: a merchant whose own `admin/design/views/home.js` (or any other copy of the default home screen) fills the stat cards with `stats.prepend` / `stats.append` from the request callbacks should take the same fixed-slot change from `admin/design-defaults/views/home.js` (a `place(slot, node)` helper); without it the cards can swap places while the requests finish, nothing breaks. A merchant whose `public/index.html` contains an inline `<svg>`, `<math>`, `<select>` or `<frameset>` gets a guard warning (an error in the template) and should move it into `app.js` or a file under `public/assets/`.

## v0.5.0 (2026-11-28)

Release summary. Everything below is a human-reviewed core change; every manifest was re-locked with the documented `--update` commands. From v0.4.1 a sync brings in two sections: v0.4.2 (D12, guard tightening, below) and this one (D13 to D23). Parts of this release only RESTRICT the design layer (D12, D17 to D20, D23): a design file that passed the v0.4.1 guard can be refused now, and a design layer that depends on a core module or a global that is now sealed can fail at run time. Read MIGRATION and "Known limits" first.

What is new: the design history (read layer, review dialog and actions, default screens, design_enabled gating: D13 to D16), the scan and runtime hardening of stage A (D17 to D20, D23), the personal profile page (D21) and real-browser tests in CI (D22). The hardening makes some attacks harder and the damage of a bypass smaller. It is NOT isolation: the design layer still runs in the same page and the same origin as the core (see "Known limits").

### MIGRATION: read before the first sync-core to v0.5.0

1. Create and fill `merchant.headers.json` BEFORE the first sync (human, once, per merchant repo made before v0.5.0). The running `sync-core` is the OLD one, which does not know this file, so the file must already exist when the new guards run at the end of the sync. In the merchant repo:
   * Copy `merchant.headers.json` from the template checkout (at tag v0.5.0) to the merchant repo root.
   * Set `apiOrigin` to the origin of `apiBase` in your `public/config.js` (for example `https://api.example.com`, no path) and `imageOrigin` to the host that serves your product image URLs (look at the `image` URLs of your catalogue, for example `https://img.example.com`). Both are required, both must be bare lower-case `https` origins: no path, no trailing slash, no wildcard, no IP address, no `localhost`, no `https:` / `*` / `data:`. Optional lists `extraConnect`, `extraImg`, `extraFont`, `extraStyle`, `extraFrame` (and `extraRules` for Cache-Control only) are for anything else you really need; leave them empty otherwise. Do not leave any `replace-with-*` placeholder: in a merchant repo that is an ERROR.
   * Render the CSP file with the TEMPLATE's renderer: `node <template checkout>/scripts/render-headers.mjs --root . --core <template checkout>/scripts/headers.core.txt` (writes `public/_headers`). Commit both files. The working tree must be clean for the sync.
   * Then run the sync as usual: `node scripts/sync-core.mjs --from <template checkout at tag v0.5.0> --dry-run`, then with `--yes --ack-design-actions` (below).
2. Adopt the design history routes BEFORE the sync (found by the release check, and it contradicts the older sentence "without the routes the built-in screens are used"). The admin guard test `scripts/test-design-history.mjs`, which the sync runs for verification, asserts that the merchant's own `admin/design/routes.js` maps `design` to `views/design-history.js`, and the design check requires every mapped file to exist. So before the sync, copy from the template checkout to the merchant repo: `admin/design/views/design-history.js`, `admin/design/views/design-request.js`, `admin/design/parts/design-history-parts.js`, and add the two entries `design: "views/design-history.js"` and `designRequest: "views/design-request.js"` to `admin/design/routes.js` (or copy the template's whole `admin/design/` if you never customised it). Commit. Without this the sync fails at verification and rolls back (exit 1: "both default views are registered ... FAIL" or "schema/routes ... the file does not exist"). The copy keys, `theme.css` block and shell changes can follow after the sync. A merchant coming from v0.4.1 must also have done the v0.4.2 design rewrites (the v0.4.2 section below) first, otherwise the D12 scan refuses its design files and the sync rolls back.
3. What happens if `merchant.headers.json` is missing or invalid. A merchant repo whose `sync-core` is already v0.5.0 or newer refuses up front, changes nothing and exits 2 with "merchant.headers.json is missing ..." and the migration steps; an invalid file (not JSON, a wildcard, an `http:` origin, a placeholder, a line over 2000 characters, ...) is refused the same way, also by `--dry-run`, with the validation messages. A v0.4.x `sync-core` (the normal first sync) cannot know the file: it copies the new core, then runs the new guards, which refuse a missing or invalid `merchant.headers.json` and a `public/_headers` that is not the exact rendering; the sync then fails and ROLLS BACK every file it changed (exit 1), so a forgotten step costs a rollback, not a half-applied sync (release check: a v0.4.2 merchant without the file got "merchant.headers.json is missing ... (copy it from the template checkout, set apiOrigin and imageOrigin, then run render-headers ...)" plus "CSP connect-src must list explicit origins only"; an invalid file got "merchant.headers.json: apiOrigin ... wildcards are not allowed"; both ended with "SYNC FAILED, every file was restored" and a clean working tree; fix the file and run the sync again).
4. Roll back: `git reset --hard && git clean -fd` DISCARDS ANY UNCOMMITTED WORK and only returns to the last commit, which is the state with the prerequisites committed (that state itself does not pass the OLD guards, see step 9). Use it only right after a failed or unwanted sync, when nothing else is uncommitted. The sync never commits.
5. If the image host is not the one in `imageOrigin`, the browser blocks the product photos (a CSP violation in the console); fix the origin in `merchant.headers.json`, run `node scripts/render-headers.mjs`, commit. The file is human-only: a design session may not edit it (`check-scope` refuses it) and a sync never overwrites it. After v0.5.0 every sync re-renders `public/_headers` from the new core template and your `merchant.headers.json`; manual edits of `public/_headers` are LOST (the sync prints the differing lines first); use `extraRules` (Cache-Control only) for long-cache headers.
6. Until a merchant syncs it keeps its old storefront CSP (`connect-src` and `img-src` allow any `https:` origin).
7. `sync-core --ack-design-actions`: v0.5.0 carries "Design-layer action:" lines, so `sync-core` applies nothing and exits 3 until a human passes `--ack-design-actions` together with `--yes`. Read the actions listed (they are the lines below) first; most are optional adoption of the new default screens, a few are required for a merchant design that uses the patterns listed under "Compatibility".
8. New merchants (`node scripts/new-merchant.mjs ... --api-base <apiBase> --image-origin <image origin>`) get a filled `merchant.headers.json` and a rendered `public/_headers`; without `--image-origin` the placeholder stays and the guard reports an ERROR until a human fills it in.
9. ONE branch, merged together. The prerequisites (merchant.headers.json, the rendered public/_headers, the three design-history view files and the two routes.js entries) and the sync itself must be done on ONE branch and merged to main together. Do not merge the prerequisites alone and do not let CI run on them: the OLD guards fail on them until the sync has completed (old check-layers: "locked file changed: public/_headers"; old check-design: unknown route / ctx). Commit the prerequisites on the sync branch only.
10. Release order (template maintainers): after the release PR is merged, create the annotated tag v0.5.0 on the merge commit of main, push it, and only then create merchants with new-merchant or run sync-core; otherwise `.template-version` records "NOT at tag" and sync-core refuses the source.

Deploy requirements (host, not design layer):
* Admin host: every host that serves the admin (production, preview hosts, the AI-edit service's preview environments) must run the v0.5.0 `admin/deploy` files: the inline import map in `admin/index.html` needs `script-src 'self' 'sha256-<hash of the map text>'` in the CSP (server level and `/site-config.js`; the guard checks the hash and `check-design.mjs --update` rewrites it), `/deny/` must answer 404 and any request path with an encoded slash (`%2f`), backslash (`%5c`) or dot (`%2e`) or a double slash must be refused (404; the template's nginx config does both). Another web server must reproduce all three. A host that lacks any of this does not break the admin: the fail-closed canary turns the custom design OFF, the built-in screens and a calm note are shown and the console warns.
* `ADMIN_SITE_ORIGIN` (the storefront origin, `https://host[:port]`, lower case; required since v0.3.0, the admin image refuses to start without it) must be set. A reminder for merchants jumping from versions before v0.3.0.
* `ADMIN_UPLOAD_ORIGIN` must cover the host of the platform's signed screenshot URLs (the object-storage account endpoint), otherwise the review dialog cannot load the before / after screenshots (D14).
* Preview hosts need `ADMIN_PREVIEW_MODE` (`version` or `change`, optional `ADMIN_PREVIEW_TAG`, `ADMIN_PREVIEW_EXPIRES`) and their origin registered in the platform's `ADMIN_PREVIEW_ORIGINS`, otherwise the login is refused (D18).
* Storefront host: Cloudflare must serve `public/_headers` as rendered. A host that does not read that file must carry the same policy (D1, D20).

Compatibility warning (D23, also D17 and D20): the stricter scans refuse code that earlier versions accepted. In particular a variable, parameter or arrow function named `open` that is CALLED (`open(url)`), and destructuring or aliasing of `window.location` / `window.history` (and of `open`, `location`, `history` from `window`, `globalThis`, `self`, `top` or `parent`), is now rejected by the storefront scan; rename it or use `location` / `history` directly. Escaped spellings of banned names, `ev["view"]`, `el["onclick"] = fn`, `fetch`, `sendBeacon`, `WebSocket`, `EventSource`, `XMLHttpRequest`, `new Image()` and `window.open` (also through aliases or computed names) in the storefront design, and dialog / popover / synthetic-input / DOM-traversal patterns in the admin design (D12), are refused. The template's own design layer has zero violations; a merchant design must be checked with `node scripts/check-layers.mjs --check` and `node admin/scripts/check-design.mjs` after the sync (a failing sync is rolled back).

### Known limits (stated plainly)

* Sealing is not isolation. The API seal, the frozen intrinsics and the import map make the core's own client and token unreachable and make poisoning built-ins and importing core modules fail, but a design module is still same-realm and same-origin code: it can read and change the DOM, call everything `ctx` hands out, call the platform's cookie refresh endpoint itself, and hide or distort the page BEHIND a core dialog. Isolation (a separate origin, a sandboxed iframe or worker, a DSL) is postponed, not done (D16, D18, D19).
* Only Chromium was run. Firefox and Safari are NOT verified for the import map, the CSP hash and the freeze; the fail-closed canary turns the custom design OFF in a browser that does not enforce the map instead of leaving it unprotected. Verify them before relying on a custom design there (D19).
* The static scans are token and regular-expression scans, not parsers. D23 lists what they do not see (a file-wide exemption of a name the file declares anywhere, incomplete aliasing, non-literal keys, `this.open`, `with`, passing `window` as an argument, `location['href'] = ...`), D17 the data-flow limits (an alias that never spells its name, `${}`-split template text), and the HTML comment handling does not know raw-text elements (`<style><!-- </style><script>...`), so an inline script can still hide from the `index.html` check. The real fences are the strict CSP (script-src, connect-src and img-src pinned to the merchant's origins, D20; the hash for the import map, D19), the core-owned dialogs and the human approval.
* Storefront egress that no CSP directive governs remains: top-level navigation, DNS prefetch hints, and requests to the merchant's own API and image origins. The design layer renders the customer's checkout form, so it necessarily holds that data; the order access token is still handed to it (D20, follow-ups listed there).
* The vendored HEIC decoder's worker evaluates a string, which the CSP forbids, so the HEIC fallback of image upload cannot run (browsers that decode HEIC natively are unaffected; D18).
* The import-map wall depends on the server (a redirect from a `/design/` URL to a core file would escape it), the canary tests its own scope and not the design scope, and several `lib/` data modules are not sealed by name (the map is their wall; D19).
* The profile hint can show once more after a name was set in another tab or device; the e2e noise of `parity.mjs` and one `run.mjs` search timeout are not fixed; the suites that need the ecommerce stack run locally only (D22, D23).

### 6. Runtime hardening: sealed API, frozen intrinsics, preview host (D18)

Runtime hardening, PR 2 of the stage A security plan (decision D18 in docs/DECISIONS.md, owner-approved 2026-11-27; human-reviewed core change; manifests re-locked with `--update` on the branch `core/admin-runtime-hardening`). Only RESTRICTS the design layer: no new ctx function, no guard rule, no CSP change. (1) Sealed API capability: `lib/api.js` keeps the client and the token in its closure and exports only `ApiError`, `takeApi()` (boot phase only) and `sealApi()` (called by `app.js` before the design layer is imported); there is no `tokens` export and no `.access` getter, and `lib/session.js` no longer re-exports `restoreSession`. (2) Frozen intrinsics: new `lib/lockdown.js` freezes the language and web-platform prototypes and namespaces the core's data passes through and locks `fetch`, `XMLHttpRequest`, `Promise`, `JSON` and the other listed bindings on `window`, after the seal and before the design layer loads (`Error.prototype.name` and a few other keys stay assignable on instances). `heicHooks` is frozen and the vendored HEIC decoder is taken out of `window` as soon as it ran. (3) Preview host: a session on a preview host must carry the platform's `scope: "preview_ro"` or it is dropped; a 403 `preview_read_only` shows the fixed message "this is a preview, go back to the normal admin to edit" (no probe, no logout); an ended preview session asks to log in again. Operators: set `ADMIN_PREVIEW_MODE` (+ `ADMIN_PREVIEW_TAG`, `ADMIN_PREVIEW_EXPIRES`) on the preview host and register its origin in the platform's `ADMIN_PREVIEW_ORIGINS` (admin/README.md "預覽主機", admin/docs/DESIGN-LAYER.md). (4) The approve button and the reject confirmation of the review dialog stay disabled for 1 second after the dialog appears, with a countdown. (5) The review dialog shows the scan report: guard verdict with rule ids and violation count, the checked sha next to the sha to approve (warning on mismatch), guard version and time, the file count and the full collapsed list of changed paths, and "run by the service, not verified by the platform". Offline suites sign in through `admin/scripts/lib/test-signin.mjs` instead of `tokens.set`.

Second follow-up: window accessors (`innerWidth`, `innerHeight`, `devicePixelRatio`, `visualViewport`, `name`, `opener`, `on*`, ...) are made non-configurable without a setter, and the dialog-in-viewport check and the preview banner read the viewport through getters captured in `lib/natives.js`.

Follow-up after the independent review of the same PR: the intrinsics freeze is an enumeration of the global object (every constructor, namespace and binding, plus the singleton instances `document`, `performance`, ...; explicit `EXCEPTIONS` list), `lib/natives.js` captures the natives the core's own checks use (clock, getComputedStyle, matchMedia, requestAnimationFrame), the approve countdown is a once-per-second non-live text with one polite announcement and an `aria-disabled` (focusable, described) button, preview hosts distinguish "not a preview host", "preview expired" and a generic refresh failure, and a failed guard report is documented as display-only.

Design-layer action: none; no design file had to change (the template's own `admin/design` and `admin/design-defaults` are untouched). A merchant's own design code that imported `/lib/api.js` or any other core module was already refused by the guard and now also fails at run time. * Platform CORS requirement for the storefront content request (browser, cross-origin to the platform API): the platform must allow the request headers If-None-Match and X-Preview-Token, and expose the response header ETag (Access-Control-Expose-Headers: ETag). Without it revalidation and preview do not work (content still loads, uncached).
* Storefront images in content: a content image is shown only if its origin is one the catalogue returned or SHOP_CONFIG.imageOrigin. The catalogue usually arrives after the content, so the core now re-notifies listeners when the catalogue adds an image origin (the page repaints); set SHOP_CONFIG.imageOrigin in public/config.js to have them at the first paint.
* A merchant that does nothing keeps working: unpublished or missing documents fall back to public/content.js, and the admin uses its built-in default screens.
